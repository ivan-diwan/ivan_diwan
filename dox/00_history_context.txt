Контекст программы: внешний и внутренний порядок существования
1. Общее назначение программы
Программа представляет собой простой визуальный редактор геометрии формы для PySide6.
Ее задача — позволить пользователю:
создать новую форму или загрузить существующую
визуально, мышью, собирать форму из реальных объектов PySide6
размещать объекты на форме
изменять их размеры
выбирать объект кликом
редактировать его свойства в отдельной панели
удалять выбранный объект
сохранять итог формы в Python-файл
При этом программа должна быть максимально практичной, простой в использовании и не перегруженной лишней функциональностью.
2. Общий принцип работы программы
Программа должна быть построена по схеме:
внешне пользователь работает с двумя окнами
внутренне программа всегда работает через активный промежуточный JSON-документ формы
итоговое сохранение выполняется в Python-файл
загрузка должна поддерживать и JSON, и Python
для этого нужен двусторонний конвертер JSON ⇄ Python
3. Внешнее существование программы
Это то, как программа существует для пользователя.
3.1. После запуска программы
После запуска существует только главное окно редактора.
Это узкое вертикальное окно, на всю высоту экрана.
В нем расположены 4 зоны сверху вниз:
1. Узкая верхняя полоса
Кнопки:
Создать
Загрузить
Сохранить
2. Основная прокручиваемая зона
Список доступных объектов PySide6.
Примерный состав:
QLabel
QPushButton
QLineEdit
QTextEdit
QComboBox
QCheckBox
QRadioButton
QFrame
QGroupBox
QTabWidget
3. Зона свойств выбранного объекта
Поля для редактирования параметров выбранного объекта.
Здесь отображаются:
имя объекта
геометрия
текстовые свойства
другие допустимые свойства по типу объекта
4. Нижняя зона
Кнопка:
Удалить объект
Дополнительно удаление выбранного объекта должно работать по клавише:
Del
3.2. Что отсутствует при запуске
После запуска программы:
формы не существует
активного документа формы не существует
отдельного окна формы не существует
рабочая область формы еще не открыта
Это важное правило.
До нажатия Создать или Загрузить пользователь видит только левое окно редактора.
3.3. Что происходит при нажатии Создать
При нажатии Создать:
создается новый документ формы
создается новый промежуточный JSON-файл формы
этот JSON-документ становится активным документом программы
на его основе открывается отдельное независимое окно формы
в этом окне показывается пустая форма
Именно с этого момента форма начинает существовать.
3.4. Что происходит при нажатии Загрузить
При нажатии Загрузить пользователь выбирает файл формы.
Программа должна понимать два формата:
JSON
Python
После выбора файла:
если выбран JSON — он читается напрямую
если выбран Python — он сначала переводится в JSON через конвертер
полученный JSON-документ становится активным документом программы
на его основе открывается отдельное окно формы
в этом окне отображается загруженная форма
3.5. Работа пользователя после открытия формы
После Создать или Загрузить пользователь работает уже с двумя окнами:
Левое окно редактора
Используется для:
выбора объекта из списка
редактирования свойств выбранного объекта
удаления объекта
команд создать / загрузить / сохранить
Отдельное окно формы
Используется для:
drag&drop объектов на форму
выбора объекта мышью
перемещения объекта
изменения размеров объекта
визуальной работы с контейнерами и вкладками
3.6. Добавление объекта
Пользователь:
выбирает объект в списке
захватывает его мышью
перетаскивает в окно формы
отпускает в нужной точке
После этого объект появляется на форме.
3.7. Выбор объекта
Пользователь кликает по объекту в окне формы.
После этого:
объект выделяется
в левом окне открываются его свойства
становится доступным удаление именно этого объекта
3.8. Перемещение и изменение размера
Пользователь мышью:
двигает объект по форме
изменяет его размер
На экране это должно происходить сразу визуально.
3.9. Изменение свойств
Когда объект выбран, пользователь в левом окне может менять:
имя
координаты
размеры
текст
title
placeholder
checked
items
другие допустимые свойства по типу объекта
3.10. Удаление объекта
Удаление выбранного объекта должно происходить:
кнопкой Удалить объект
клавишей Del
3.11. Сохранение формы
При нажатии Сохранить:
текущая форма сохраняется в Python-файл
Для пользователя это выглядит так:
форма собрана
нажал Сохранить
получен .py файл формы
4. Внутреннее существование программы
Это то, как программа реально устроена внутри.
4.1. Главный внутренний принцип
Программа должна работать не напрямую с Python-файлом, а через активный промежуточный JSON-документ формы.
То есть:
JSON — основной рабочий внутренний формат
Python — внешний итоговый формат
редактор всегда редактирует JSON-документ
Python-файл генерируется из JSON
Python-файл при загрузке сначала переводится обратно в JSON
4.2. Что является центром системы
Центр программы — это:
активный документ формы
Он существует:
в памяти
как живая модель формы
и соответствует текущему JSON-документу
Это главный источник истины.
Не окно формы, не список объектов и не Python-файл.
4.3. Состояния программы
Программа существует в двух основных состояниях:
Состояние 1 — без активного документа
После запуска:
документа формы нет
JSON-документа нет
окна формы нет
Состояние 2 — с активным документом
После Создать или Загрузить:
есть активный JSON-документ
есть модель формы в памяти
есть отдельное окно формы
все действия меняют этот документ
4.4. Что происходит при Создать
При Создать программа:
создает новый JSON-документ формы
этот JSON становится активным документом
на основе него создается отдельное окно формы
пустая форма визуализируется на экране
Пример стартового JSON:
JSON
{
  "form": {
    "id": "form_root",
    "width": 1200,
    "height": 800
  },
  "objects": []
}
4.5. Что происходит при Загрузить
Программа должна иметь отдельный двусторонний конвертер:
JSON ⇄ Python
Если загружен JSON
он читается напрямую
валидируется
становится активным документом
Если загружен Python
Python переводится в JSON
JSON становится активным документом
После этого:
окно формы строится на основе активного JSON-документа
4.6. Что должен хранить активный документ формы
Активный документ формы должен содержать:
параметры самой формы
список объектов
тип каждого объекта
parent_id
геометрию
свойства объекта
4.7. Как хранится геометрия
Геометрия должна храниться как:
x
y
width
height
Но всегда относительно родителя.
То есть:
объект верхнего уровня — относительно формы
объект внутри QGroupBox — относительно QGroupBox
объект внутри TabPage — относительно TabPage
Это нужно для поддержки достаточно сложных форм, включая:
вкладки
групповые контейнеры
вложенные области
4.8. Как внутренне существует форма во время редактирования
После открытия документа программа должна синхронизировать три слоя:
1. Модель документа в памяти
Главный источник истины
2. Отдельное окно формы
Визуализация документа
3. JSON-документ
Сериализованное текущее состояние документа
4.9. Добавление объекта внутрь документа
При drag&drop объекта на форму программа должна:
определить тип объекта
определить родителя, в которого попал объект
создать запись объекта в активном документе
создать визуальный объект на форме
обновить JSON после завершенного drop
4.10. Выбор объекта
При клике по объекту:
объект помечается как выбранный
окно формы показывает выделение
левое окно загружает свойства выбранного объекта
кнопка удаления относится к нему
4.11. Перемещение объекта
Во время перемещения мышью:
объект двигается визуально сразу
Но JSON не должен переписываться на каждый пиксель.
После завершения манипуляции мышью:
новые координаты фиксируются в документе
JSON обновляется
4.12. Изменение размера объекта
Во время resize:
визуальное изменение идет сразу
После завершения resize:
размеры записываются в документ
JSON обновляется
4.13. Изменение свойств
При изменении свойств в левой панели:
обновляется модель документа
обновляется визуальный объект
обновляется JSON
4.14. Удаление объекта
При Del или кнопке удаления:
удаляется выбранный объект
удаляется его запись из документа
удаляется его запись из JSON
объект исчезает с формы
панель свойств очищается
Если удаляется контейнер:
удаляется вместе с дочерними объектами
4.15. Сохранение
При нажатии Сохранить:
берется активный JSON-документ
через конвертер выполняется JSON → Python
создается итоговый Python-файл формы
То есть Python-файл не редактируется напрямую, а генерируется из рабочего JSON.
5. Важная итоговая формулировка
Ее можно использовать как основу для другого чата:
Программа стартует только с узким главным окном редактора.
До нажатия Создать или Загрузить формы и документа формы не существует.
При Создать создается новый промежуточный JSON-документ формы, он становится активным документом программы, и на его основе открывается отдельное окно пустой формы.
При Загрузить программа принимает JSON или Python; если загружен Python, он через двусторонний конвертер переводится в JSON, после чего JSON становится активным документом.
Дальнейшая работа программы всегда идет через активный JSON-документ: drag&drop объектов, выбор, перемещение, resize, изменение свойств и удаление изменяют именно этот документ.
После завершенных манипуляций мышью и после изменения свойств JSON-документ обновляется.
При Сохранить активный JSON-документ преобразуется в Python-файл формы.
Внешне программа существует как двухоконный редактор: левое окно управления и отдельное окно формы. Внутренне программа существует как редактор живого промежуточного JSON-документа с экспортом в Python.
6. Короткая версия
Внешне:
есть узкое главное окно редактора
форма появляется отдельным окном только после Создать или Загрузить
пользователь мышью собирает форму
свойства редактирует в левом окне
удаляет объект кнопкой или Del
сохраняет в Python
Внутренне:
программа всегда работает через активный JSON-документ
JSON — канонический рабочий формат
Python — итоговый сохраняемый формат
загрузка Python идет через конвертацию в JSON
форма на экране — это визуализация активного JSON-документа

3. Общие параметры всех объектов

Эти параметры есть у каждого объекта формы.


---

id

тип: str

обязателен: да

по умолчанию: генерируется системой

редактируется пользователем: нет


Назначение: внутренний уникальный идентификатор объекта.


---

type

тип: str

обязателен: да

по умолчанию: задается при создании

редактируется пользователем: нет


Назначение: тип объекта, например QPushButton.


---

parent_id

тип: str

обязателен: да

по умолчанию: form_root или id контейнера

редактируется пользователем: нет напрямую


Назначение: указание, внутри какого родителя находится объект.


---

name

тип: str

обязателен: да

по умолчанию: генерируется по типу, например push_button_1

редактируется пользователем: да


Назначение: рабочее имя объекта.


---

x

тип: int

обязателен: да

по умолчанию: 0

редактируется пользователем: да


Назначение: координата X относительно родителя.


---

y

тип: int

обязателен: да

по умолчанию: 0

редактируется пользователем: да


Назначение: координата Y относительно родителя.


---

width

тип: int

обязателен: да

по умолчанию: зависит от типа

редактируется пользователем: да


Назначение: ширина объекта.


---

height

тип: int

обязателен: да

по умолчанию: зависит от типа

редактируется пользователем: да


Назначение: высота объекта.


---

4. Значения по умолчанию для геометрии

Нужно сразу принять правило:

у каждого типа должны быть дефолтные размеры, чтобы объект после drag&drop появлялся сразу нормально.


---

Примерный принцип:

кнопки: средние

поля: шире

контейнеры: заметно крупнее

таблицы/списки: крупные

вкладки: большие


Точные значения потом можно подправить, но принцип должен быть зафиксирован.

18. Итог

С учетом последнего обсуждения по параметрам:

общая база параметров уже определена

для каждого объекта определен минимально разумный набор

там, где есть фиксированные варианты, они перечислены

там, где важен формат, он указан


Следующий правильный шаг уже не повторять список объектов, а делать:

правила вложенности объектов

то есть:

что может быть на форме

что может быть внутри чего

где объект допустим

1. Зачем нужны правила вложенности

Если их не зафиксировать заранее, получится хаос:

объект можно будет бросить куда угодно

часть комбинаций будет визуально работать, а часть ломаться

контейнеры будут вести себя по-разному

сохранение и генерация Python будут нестабильны


Поэтому нужно сразу определить:

> какой объект может быть родителем, а какой нет



и

> какие типы детей допустимы внутри каждого родителя




---

2. Общий принцип вложенности

У нас геометрический редактор, а не layout-конструктор.
Значит базовый принцип такой:

2.1. Любой объект либо:

не может иметь детей

либо может иметь детей как контейнер



---

2.2. Вложенность определяется только через parent_id

То есть визуальная вложенность = логическая вложенность.

Если объект находится:

на форме → parent_id = form_root

в QGroupBox → parent_id = groupbox_id

в TabPage → parent_id = tab_page_id

19. Диалоговые объекты

Теперь важный вопрос про QDialog.

19.1. Как его трактовать

Есть два пути:

Вариант A

QDialog — это отдельный тип корневой формы, а не дочерний объект

Вариант B

QDialog можно вставлять как вложенный объект


---

19.2. Правильнее для нашей архитектуры

Выбрать вариант A.

То есть:

QDialog не должен быть обычным объектом внутри формы

он должен быть альтернативным корнем формы

19.3. Значит

QDialog не включаем в parent-child вложенность как обычный объект

А используем как отдельный тип корня документа:

либо FormRoot(QWidget)

либо FormRoot(QDialog)


Это архитектурно чище.

21. Что делать с menu/status/toolbar

Если мы оставляем их как объекты системы, нужно решить, как они встраиваются.

Но в рамках именно формы они не должны быть обычными дочерними геометрическими объектами.

Поэтому лучше:

не включать их в обычные parent-child правила формы

считать отдельным уровнем каркаса окна, если понадобится later


То есть сейчас:

не включаем в обычную вложенность формы.

1. Зачем нужен отдельный слой поведения

Даже если список объектов и параметров уже определен, без правил поведения редактор остается неясным.

Например, нужно заранее понимать:

можно ли взять объект из палитры и просто бросить на форму

можно ли его потом свободно таскать

можно ли менять размер

что будет, если бросить QPushButton на QTabWidget

что будет, если выбрать QScrollArea

как создается новая вкладка

как удаляется страница


То есть теперь задача такая:

> каждый тип объекта должен получить четкую редакторскую роль

один клик мышью по объекту

Что делает редактор

1. снимает выделение с предыдущего объекта


2. выделяет текущий объект


3. показывает рамку/маркеры выделения


4. загружает параметры в панель свойств


5. активирует кнопку удаления




---

10. Перемещение объекта

Как пользователь действует

зажимает объект мышью

тянет его внутри допустимой области

отпускает



---

Что делает редактор

1. во время движения показывает живое перемещение


2. не меняет файл на каждый пиксель


3. при отпускании:

фиксирует новые x/y

при необходимости обновляет родителя, если объект перенесен в другой контейнер

обновляет документ

обновляет промежуточный файл





---

11. Изменение размера объекта

Как пользователь действует

тянет мышью за маркер размера

изменяет ширину/высоту



---

Что делает редактор

1. визуально меняет размер объекта


2. после завершения действия:

фиксирует width/height

при необходимости корректирует x/y

обновляет документ

обновляет файл





---

12. Изменение свойств через панель

Как пользователь действует

выбирает объект

меняет значения в панели свойств



---

Что делает редактор

1. обновляет модель объекта


2. тут же применяет изменения к визуальному объекту


3. записывает изменения в документ


4. обновляет промежуточный файл




---

13. Удаление объекта

Как пользователь действует

нажимает Del или

нажимает кнопку “Удалить объект”



---

Что делает редактор

1. проверяет, выбран ли объект


2. удаляет объект из документа


3. удаляет его детей, если это контейнер


4. удаляет визуальное представление


5. очищает панель свойств


6. обновляет файл




---

14. Специальное правило удаления контейнера

Если удаляется контейнер, то:

удаляется весь его поддеревянный контент

удаляются все внутренние страницы, если это page-based контейнер

документ должен остаться целостным


Это обязательно.


---

15. Поведение обычных листовых объектов

Листовые объекты:

создаются drag&drop из палитры

могут жить только в допустимом родителе

двигаются мышью

меняют размер мышью

редактируются через панель

удаляются напрямую


Они не имеют:

внутренних детей

внутренних страниц

специальных режимов выбора



---

16. Поведение обычных контейнеров: QWidget, QFrame, QGroupBox

Теперь отдельно.


---

17. Создание контейнера

Пользователь:

берет контейнер из палитры

бросает на форму или в другой контейнер


Редактор:

создает контейнерный объект

отображает прямоугольную область

делает ее выбранной

разрешает потом бросать в нее дочерние объекты



---

18. Выбор контейнера

При клике контейнер выбирается как обычный объект.

Но дополнительно:

редактор должен ясно показывать его границы

пользователь должен понимать, что это контейнер, а не просто декоративная рамка



---

19. Движение и resize контейнера

Контейнер:

можно двигать

можно менять размер


Но при этом нужно правильно вести детей.


---

Правило

При перемещении контейнера:

дети не теряют свои локальные координаты

меняется только положение контейнера

дети визуально переезжают вместе с ним


При resize контейнера:

дети не должны автоматически перестраиваться, если не включена специальная логика

по умолчанию геометрия детей остается прежней


Это соответствует геометрической модели.


---

20. QGroupBox как особый обычный контейнер

Он ведет себя как контейнер, но имеет:

заголовок

опциональный checked/checkable режим


С точки зрения редактора:

это контейнер с визуальным заголовком

дети размещаются в его внутренней области

координаты детей считаются от внутренней клиентской области



---

21. Специальные контейнеры: общий принцип

Теперь группа, где обычного drag&drop уже недостаточно.

У специальных контейнеров есть два уровня поведения:

1. внешний — они как обычные объекты ставятся на форму


2. внутренний — они управляют детьми по особым правилам




---

22. QScrollArea — поведение

Как создается

Пользователь бросает QScrollArea на форму как обычный контейнер.

Редактор:

создает сам QScrollArea

автоматически создает внутреннюю сущность ContainerContent

связывает ее с scroll area



---

Что видит пользователь

На форме видит сам scroll area как рамку/область.

Внутреннее содержимое не выглядит как отдельный объект палитры.


---

Как добавляются дети

Если пользователь бросает объект внутрь scroll area:

объект реально добавляется не в QScrollArea

а в ContainerContent



---

Как выбирается

Можно выбирать:

сам QScrollArea

объекты внутри него



---

Как двигается и ресайзится

Сам QScrollArea:

двигается

меняет размер


Внутреннее содержимое остается дочерним контейнером.


---

23. QSplitter — поведение

QSplitter сложнее.


---

Как создается

Пользователь бросает splitter на форму.

Редактор создает:

объект splitter

начальную структуру из двух панелей



---

Главный принцип

Splitter не должен существовать пустым без внутренних зон.
После создания он сразу должен иметь как минимум 2 области.


---

Что это значит архитектурно

Внутри splitter должны существовать внутренние контейнерные панели.

Можно реализовать это через:

обычные QWidget-панели, создаваемые автоматически или

специальную внутреннюю сущность, если нужна строгая модель



---

Что видит пользователь

На форме он видит:

две разделенные области

разделитель между ними



---

Как добавляются дети

Пользователь бросает объекты:

не в сам splitter целиком

а в одну из его внутренних панелей



---

Как двигается и ресайзится

Весь splitter:

двигается как единый объект

ресайзится как единый объект


Внутренние панели:

меняют размеры через сам splitter

не должны свободно двигаться отдельно как самостоятельные объекты палитры



---

Что должен уметь пользователь

менять orientation

менять размеры панелей

возможно добавлять панели позже, если это поддерживается


Но базово лучше зафиксировать:

splitter начинается с двух панелей



---

24. QTabWidget — поведение

Это один из ключевых объектов.


---

Как создается

Пользователь бросает QTabWidget на форму.

Редактор автоматически создает:

сам QTabWidget

как минимум две страницы:

TabPage 1

TabPage 2




---

Что видит пользователь

На форме он видит tab-контейнер с вкладками.


---

Как выбирается

Можно выбирать:

сам QTabWidget

отдельный объект внутри активной вкладки


TabPage как внутренняя сущность напрямую на форме не выбирается как обычный прямоугольник, если не нужно.
Но в панели свойств и в логике редактора она должна существовать.


---

Как добавляются дети

Если пользователь бросает объект внутрь видимой области активной вкладки:

объект добавляется в текущую TabPage



---

Что должно быть в свойствах QTabWidget

Пользователь должен иметь возможность:

менять current_index

добавлять вкладку

удалять вкладку

переименовывать вкладку

возможно менять порядок вкладок



---

Что должно происходить при удалении вкладки

удаляется соответствующая TabPage

удаляются все дочерние объекты этой страницы



---

25. TabPage — поведение

TabPage не появляется в палитре.


---

Как создается

Создается только:

автоматически вместе с QTabWidget или

по команде “Добавить вкладку”



---

Как используется

Является реальным контейнером для объектов внутри вкладки.


---

Что пользователь может у нее менять

Минимально:

title



---

Как удаляется

Удаляется только через операции QTabWidget, а не как обычный объект формы.


---

26. QToolBox — поведение

Очень похоже на вкладки, только другая визуальная модель.


---

Как создается

Пользователь бросает QToolBox на форму.

Редактор автоматически создает:

сам toolbox

как минимум две секции (ToolPage)



---

Как добавляются дети

Если пользователь бросает объект в активную секцию:

объект попадает в соответствующую ToolPage



---

Что должно быть в свойствах

current_index

добавить секцию

удалить секцию

переименовать секцию



---

27. QStackedWidget — поведение

Это контейнер страниц без видимых вкладок.


---

Как создается

Пользователь бросает QStackedWidget на форму.

Редактор автоматически создает:

stacked widget

как минимум две страницы (StackPage)



---

Как пользователь управляет страницами

Так как визуальных вкладок нет, редактор должен дать отдельный интерфейс:

список страниц

переключение активной страницы

добавление

удаление

переименование


Это должно быть в панели свойств или в отдельной встроенной панели управления контейнером.


---

Как добавляются дети

Объекты, брошенные в видимую страницу, попадают в активный StackPage.


---

28. StackPage — поведение

Не палитра, а внутренняя страница stacked-контейнера.

Пользователь напрямую не создает ее drag&drop.

Редактирует только через свойства QStackedWidget.


---

29. QToolBox / QStackedWidget / QTabWidget — общий шаблон

У всех page-based контейнеров должен быть единый паттерн поведения:

контейнер создается пользователем

страницы создаются редактором автоматически

страницы не лежат в палитре

объекты попадают в активную страницу

страницы управляются через свойства контейнера


Это сильно упрощает систему.


---

30. QWizard — поведение

Если включаем в систему, он должен вести себя аналогично другим page-based контейнерам.


---

Как создается

Пользователь бросает wizard на форму.

Редактор создает:

wizard

минимум две страницы (WizardPage)



---

Как управляются страницы

Через свойства QWizard:

добавить страницу

удалить страницу

переименовать страницу



---

Как добавляются дети

Дочерние объекты попадают в активную WizardPage.


---

31. Dialog-объекты

Теперь отдельно про QDialog и QDialogButtonBox.


---

32. QDialog — поведение

Как уже зафиксировано, лучше считать QDialog не обычным дочерним объектом формы, а типом корня документа.

То есть пользователь не должен бросать QDialog на существующую форму.

Вместо этого:

форма создается либо как обычная форма

либо как dialog-форма



---

Следствие

QDialog не участвует в обычном drag&drop редактора как дочерний объект.


---

33. QDialogButtonBox — поведение

Это обычный leaf/container-like control без детей.


---

Как создается

drag&drop как обычный объект


Как редактируется

через список стандартных кнопок

через orientation


Как ведет себя

двигается

ресайзится

удаляется как обычный объект



---

34. Layout-объекты

С учетом нашей архитектуры их лучше не делать обычными геометрическими объектами палитры.

Если они вообще будут существовать, то как специальный внутренний механизм, а не как основной способ работы пользователя.

Поэтому их поведение в текущей системе не должно быть ядром.


---

35. Выбор объекта внутри специальных контейнеров

Нужно зафиксировать общее правило.


---

Пользователь кликает по дочернему объекту внутри контейнера

Тогда:

выбирается дочерний объект

не контейнер


Пользователь кликает по свободной области контейнера

Тогда:

выбирается сам контейнер


Это делает редактор предсказуемым.


---

36. Drag&drop между контейнерами

Важный вопрос.


---

Если пользователь перетаскивает существующий объект из одного контейнера в другой

После отпускания мыши редактор должен:

1. определить новый контейнер-родитель


2. пересчитать локальные координаты относительно нового родителя


3. обновить parent_id


4. обновить документ


5. обновить файл




---

37. Что нельзя разрешать

Нужно зафиксировать и ограничения.


---

Нельзя:

бросать объект в leaf-object

бросать обычный объект прямо в QTabWidget, минуя TabPage

бросать объект прямо в QToolBox, минуя ToolPage

бросать объект прямо в QStackedWidget, минуя StackPage

бросать объект прямо в QScrollArea, минуя ContainerContent



---

38. Поведение внутренних сущностей

Нужно зафиксировать общий принцип:

TabPage

ToolPage

StackPage

WizardPage

ContainerContent


не являются обычными объектами палитры.

Они:

создаются автоматически

управляются через родительский контейнер

существуют в документе как реальные сущности

могут быть скрыты от прямого визуального редактирования как самостоятельные объекты



---

39. Финальная матрица поведения по типам


---

Листовые объекты

drag from palette: да

move: да

resize: да

contain children: нет

delete directly: да



---

Обычные контейнеры

drag from palette: да

move: да

resize: да

contain children: да

delete directly: да, вместе с детьми



---

Специальные контейнеры

drag from palette: да

move: да

resize: да

contain children directly: нет

contain internal pages/areas: да

delete directly: да, вместе с внутренней структурой



---

Внутренние страницы

drag from palette: нет

move as free object: нет

resize as free object: нет

contain children: да

delete directly: нет, только через родительский контейнер

40. Главный итог

Теперь после этого у нас уже есть четыре фундаментальных слоя:

1. список объектов


2. параметры объектов


3. правила вложенности


4. поведение объектов в редакторе



Это уже очень серьезная основа.

41. Что дальше

Следующий правильный шаг:

структура панели свойств

То есть нужно зафиксировать:

какие поля панели показываются всегда

какие зависят от типа объекта

как показывать page-based контейнеры

как показывать специальные команды:

добавить вкладку

удалить страницу

переключить страницу

добавить панель splitter и т.д.



Именно панель свойств связывает:

модель объекта

пользователя

документ

логику специальных контейнеров


Это сейчас следующий обязательный слой.



Продолжаю. Следующий обязательный слой — структура панели свойств.

Именно панель свойств соединяет:

выбранный объект на форме

его внутреннюю модель

пользовательское редактирование

обновление промежуточного документа

специальные операции контейнеров


Если ее не продумать заранее, редактор получится неудобным даже при хорошей архитектуре объектов.


---

1. Назначение панели свойств

Панель свойств — это нижняя часть левого окна редактора.

Она должна:

показывать параметры выбранного объекта

позволять редактировать эти параметры

обновлять объект на форме

обновлять документ формы

давать специальные команды для контейнеров и страниц


То есть это не просто “таблица полей”, а центр управления выбранным объектом.


---

2. Когда панель свойств активна

2.1. До создания или загрузки формы

Панель существует визуально, но:

пустая

неактивная

без доступных полей



---

2.2. После открытия формы, когда ничего не выбрано

Панель тоже пустая либо показывает:

“Объект не выбран”



---

2.3. После выбора объекта

Панель заполняется параметрами этого объекта.


---

3. Главный принцип построения панели

Панель должна быть однообразной для всех объектов, но при этом уметь показывать специальные разделы.

То есть у нее должна быть фиксированная структура:

1. информация об объекте


2. геометрия


3. собственные свойства объекта


4. специальные действия, если объект особый




---

4. Общая структура панели свойств

Для любого выбранного объекта панель делится на блоки.


---

5. Блок 1 — Информация об объекте

Этот блок есть всегда.

Он должен показывать:

тип объекта

имя объекта

родителя



---

5.1. Поля

type

показывается всегда

только для чтения

нужен для понимания, что выбрано


Пример:

QPushButton

QTabWidget

QGroupBox



---

name

редактируется

это рабочее имя объекта



---

parent

показывается как read-only

нужен для понимания, где лежит объект


Можно показывать:

form_root

main_tabs / TabPage 1

group_main


Пользователь не должен вручную менять родителя через поле.


---

6. Блок 2 — Геометрия

Этот блок есть почти всегда.

Он должен содержать:

x

y

width

height



---

6.1. Общие правила для геометрии

редактируется вручную

обновляет объект на форме сразу после подтверждения

числа целочисленные

минимальные размеры должны быть ограничены



---

6.2. Для каких объектов геометрия обычная

Обычная геометрия редактируется у:

всех leaf-объектов

всех обычных контейнеров

всех специальных контейнеров верхнего уровня



---

6.3. Для каких объектов геометрия может быть скрыта или частично read-only

У внутренних страниц:

TabPage

ToolPage

StackPage

WizardPage

ContainerContent


геометрия не должна редактироваться как у обычного объекта мышью.

Для них:

можно скрыть блок геометрии или

показывать только read-only


Это правильнее.


---

7. Блок 3 — Собственные свойства объекта

1. Что такое документ формы

Документ формы — это единая внутренняя модель текущей формы.

Он должен описывать:

саму форму

все объекты на форме

связи между объектами

страницы и внутренние контейнерные сущности

текущую структуру редактора


Документ должен быть:

полным

однозначным

пригодным для чтения и записи

пригодным для построения окна формы

пригодным для генерации Python



---

2. Главный принцип документа

Нужно сразу принять один очень важный принцип:

> документ формы должен хранить не визуальные Qt-объекты, а нормализованные сущности редактора



То есть в документе не должны храниться:

реальные экземпляры QPushButton

реальные QWidget-объекты

указатели на виджеты


Документ хранит только:

данные

структуру

параметры

связи


А визуальные объекты уже строятся на основе документа.


---

3. Что обязательно должно быть в документе

Документ должен состоять как минимум из 4 слоев:

3.1. Метаданные документа

Что это за документ и какой у него формат.

3.2. Описание корня формы

Размеры, тип корневой формы, имя.

3.3. Список всех сущностей

Все объекты формы, включая внутренние страницы и контейнерные области.

3.4. Служебное состояние редактора

Только то, что нужно редактору для восстановления рабочего состояния, если это вообще нужно сохранять.


---

4. Что должно быть в метаданных

Метаданные не должны быть тяжелыми, но базовый минимум нужен.


---

4.1. Поля метаданных

Минимально стоит заложить:

версия формата

тип документа

возможно дата последнего изменения

возможно тип корневой формы



---

4.2. Зачем это нужно

Это позволяет:

в будущем менять формат без хаоса

понимать, что именно открывается

проверять совместимость загрузки



---

5. Корень формы

Это отдельная сущность документа.

У нас уже есть FormRoot, значит нужно зафиксировать, как он существует в документе.


---

5.1. FormRoot — это не просто запись о ширине и высоте

Он должен быть полноценным корневым объектом модели.

То есть:

у него есть id

у него есть type

у него есть name

у него есть размеры

он является верхним родителем для объектов верхнего уровня



---

5.2. Зачем это важно

Это делает модель единой:

все объекты имеют родителя

корень формы — тоже объект модели

не нужно специальных исключений в логике parent-child



---

6. Где хранить объекты

Это один из самых важных вопросов.

Есть два варианта:

Вариант A

Хранить объекты вложенными структурами

Вариант B

Хранить объекты единым плоским списком со связями через parent_id


---

6.1. Правильный вариант для нашей системы

Нужно выбрать:

единый плоский список объектов + parent_id


---

6.2. Почему это правильнее

Так проще:

добавлять объект

удалять поддерево

перемещать объект между контейнерами

пересохранять документ

конвертировать в Python

строить форму из документа



---

7. Значит главный каркас документа такой

Документ должен содержать:

meta

form

objects


где:

form — корневая форма

objects — плоский список всех остальных сущностей



---

8. Что входит в objects

В objects должны входить все объекты, кроме корня формы:

обычные controls

контейнеры

специальные контейнеры

внутренние страницы:

TabPage

ToolPage

StackPage

WizardPage


внутренние служебные контейнерные сущности:

ContainerContent, если используем



То есть документ не должен разделять:

“настоящие” объекты

“внутренние” объекты


Все должны быть реальными сущностями модели.


---

9. Почему внутренние страницы должны быть в документе явно

Это критично.

Например, если есть QTabWidget, нельзя хранить его просто как:

список названий вкладок внутри свойства


Это будет слишком слабая модель.


---

Правильнее так:

сам QTabWidget — отдельный объект

каждая вкладка (TabPage) — отдельный объект

у каждой вкладки свой id

у каждой вкладки свой parent_id

объекты внутри вкладки ссылаются на TabPage



---

Это дает:

нормальную вложенность

понятное удаление вкладки

понятное перемещение объектов

ясную генерацию Python



---

10. Минимальная структура одной сущности документа

У каждого объекта документа должен быть единый контракт.


---

10.1. Базовые поля

id

type

parent_id

name


10.2. Геометрия

x

y

width

height


10.3. Свойства

отдельный блок properties



---

11. Почему нужен отдельный блок properties

Не надо складывать все параметры объекта на один уровень.

Потому что тогда смешаются:

1. Что такое контракт сущности документа

Контракт сущности документа — это единая схема записи любого объекта формы.

То есть нужно зафиксировать:

какие поля есть у любой сущности

какие обязательны всегда

какие могут отсутствовать

какие одинаковы для всех типов

какие лежат в специальных блоках


Идея простая:

> любой объект формы, от QPushButton до TabPage, должен описываться по одной общей схеме




---

2. Зачем нужен единый контракт

Если не сделать единый контракт, начнутся исключения:

у одних объектов поля наверху

у других внутри properties

у третьих отдельная логика

у внутренних страниц своя схема


Это быстро разрушит систему.

Поэтому правильный принцип:

> все сущности редактора хранятся по одному общему шаблону




---

3. Какие сущности должны подчиняться одному контракту

Все, кроме разве что самого объекта документа.

Под контракт подпадают:

обычные controls

контейнеры

специальные контейнеры

внутренние страницы

служебные контейнерные области

корень формы, если не вынесем его в отдельный верхний блок


Но с учетом уже принятой логики правильнее сделать так:

FormRoot хранить отдельно в блоке form

все остальные — по общему контракту в objects


Это самый чистый вариант.


---

4. Какие слои должны быть у сущности

У сущности документа должны быть 5 логических слоев:

4.1. Идентификация

Кто это.

4.2. Структура

Где это находится и в каком порядке.

4.3. Геометрия

Где расположен объект и какого он размера.

4.4. Свойства

Чем этот объект отличается как тип.

4.5. Метаданные сущности

Дополнительные данные редактора, если они реально нужны.


---

5. Минимальный обязательный набор полей

Теперь фиксируем, что должно быть обязательно у любой сущности документа.


---

5.1. id

Обязательное поле.

Смысл

Уникальный идентификатор сущности.

Почему обязательно

Без него нельзя:

ссылаться на объект

строить parent-child связи

выбирать объект

удалять объект

обновлять объект


Тип

str


---

5.2. type

Обязательное поле.

Смысл

Тип сущности.

Примеры

QPushButton

QTabWidget

TabPage

ContainerContent


Тип

str


---

5.3. parent_id

Обязательное поле для всех сущностей в objects.

Смысл

Идентификатор родителя.

Примеры

form_root

group_1

tab_page_2


Почему обязательно

Это основа всей иерархии.

Тип

str


---

5.4. name

Обязательное поле.

Смысл

Рабочее имя сущности.

Почему обязательно

Имя нужно:

для генерации Python

для удобства пользователя

для панели свойств

для читаемости документа


Тип

str


---

5.5. order

Обязательное поле.

Смысл

Порядок объекта среди детей одного родителя.

Почему обязательно

Иначе порядок:

вкладок

секций

stacked-страниц

обычных объектов в одном контейнере


будет зависеть от случайного порядка в списке.

Тип

int


---

5.6. geometry

Обязательное поле почти для всех сущностей.

Это отдельный вложенный блок.

Смысл

Геометрия объекта относительно родителя.

Тип

dict


---

5.7. properties

Обязательное поле.

Смысл

Типозависимые свойства объекта.

Почему обязательно

Даже если у конкретного типа пока нет пользовательских свойств, лучше хранить пустой объект, чем делать исключения.

Тип

dict

12.2. name

id — строго уникален

name — желательно уникален, но редактор может лишь предупреждать или автоматически предлагать уникальные имена


То есть в контракте name — просто строка.

Продолжаю. Следующий слой после общего контракта сущности — контракт корня формы (FormRoot).

1. Почему FormRoot нужно описывать отдельно

Хотя логически FormRoot похож на обычную сущность, у него особая роль:

у него нет parent_id

он не лежит в общем списке objects

он не создается drag&drop

он всегда один на документ

он определяет, что именно за форма создается


То есть его нельзя бездумно смешивать с остальными объектами.


---

2. Главная роль FormRoot

FormRoot — это:

> корневая сущность документа формы, задающая базовый тип, размеры и свойства всего окна/формы



Он является:

верхним родителем для объектов верхнего уровня

точкой отсчета координат

источником общих параметров формы



---

3. Где должен храниться FormRoot

Правильный вариант:

в документе есть отдельный верхний блок form

этот блок и есть FormRoot


То есть структура документа логически должна быть:

meta

form

objects


где:

form = отдельный корневой объект

objects = все остальные сущности



---

4. Почему FormRoot не надо класть в objects

Потому что тогда появятся лишние нестыковки:

придется делать для него исключение по parent_id

он будет выглядеть как обычный объект, хотя это не так

логика документа станет менее читаемой


Гораздо чище:

form отдельно

все остальные — в objects



---

1. Назначение JSON-документа

JSON-документ — это канонический внутренний рабочий формат формы.

Он нужен для того, чтобы:

редактор открывал форму

редактор строил по нему визуальное окно формы

редактор сохранял все изменения

конвертер генерировал из него Python

Python потом можно было обратно привести к JSON


То есть JSON — это не “просто временный файл”, а главный источник истины для формы.


---

2. Главный принцип структуры JSON

Документ должен быть:

простым

однозначным

стабильным

пригодным для двусторонней конвертации

пригодным для проверки валидности

не перегруженным editor-only состоянием

Даже если объект не имеет пользовательских свойств, нужно хранить:

"properties": {}

Это сохраняет единый контракт и убирает исключения.


---

10.2. Примеры

QPushButton

"properties": {
  "text": "Сохранить"
}

QGroupBox

"properties": {
  "title": "Основные данные",
  "checkable": false,
  "checked": true
}

QComboBox

"properties": {
  "items": ["A", "B"],
  "current_index": 0,
  "editable": false
}


---

11. Нужно ли в JSON хранить editor-only состояние

Нет.

Нельзя хранить в основном JSON-документе:

выбранный объект

состояние drag

временный resize

координаты окна редактора

открытые панели

масштаб холста


Это не часть формы.


---

12. Нужно ли в JSON хранить children-массивы

Нет.

То есть не надо делать так:

{
  "id": "group_1",
  "children": ["obj_1", "obj_2"]
}


---

Почему

Потому что это дублирует структуру, которая уже задана через parent_id.

Если хранить и children, и parent_id, придется постоянно держать их в синхронном состоянии.

Правильнее:

только parent_id

children вычисляются



---

13. Нужно ли в JSON хранить порядок объектов как порядок в массиве

Нет, на массив полагаться нельзя.

Порядок должен храниться явно в order.


---

Почему

Это делает документ устойчивым:

порядок не зависит от случайной перестановки в списке

страницы вкладок всегда имеют предсказуемый порядок

объекты внутри контейнера сортируются однозначно



---

14. Правила валидности JSON-документа

Теперь нужно зафиксировать базовые правила валидности.


---

15. Документ валиден, если:

15.1.

Есть блок meta

15.2.

Есть блок form

15.3.

Есть блок objects

15.4.

meta.format_version существует и поддерживается

15.5.

meta.document_type == "pyside6_form"

15.6.

form.id == "form_root" или другой зафиксированный root-id, если это допускается

15.7.

У всех объектов в objects есть:

id

type

parent_id

name

order

geometry

properties


15.8.

У всех id уникальные значения

15.9.

Любой parent_id либо:

равен form_root

либо ссылается на существующий объект


15.10.

geometry.width > 0 и geometry.height > 0

15.11.

Тип объекта входит в поддерживаемый реестр типов


---

16. Документ невалиден, если:

отсутствует meta

отсутствует form

отсутствует objects

два объекта имеют один и тот же id

есть объект с неизвестным parent_id

есть объект без geometry

есть объект без properties

root_widget_type не входит в допустимые значения

у page-объекта неверный тип родителя

у leaf-объекта есть недопустимая структура children, если кто-то решит это добавить

Да.

Если форма пустая, это валидный документ:

"objects": []

"window_title": ""

23. Нужно ли JSON сортировать

Для удобства чтения — желательно.

Практичное правило:

objects могут храниться отсортированными:

сначала по родителю

потом по order



Но это не обязательно как правило формата.
Это можно считать правилом сериализатора.


---

24. Нужно ли хранить null-поля

Лучше избегать лишних null, если параметр можно просто не включать в properties.

Например:

Хорошо:

"properties": {
  "text": "OK"
}

Хуже:

"properties": {
  "text": "OK",
  "placeholder": null
}

То есть:

базовые обязательные поля — всегда есть

в properties держим только реально используемые значения


Это делает JSON чище.


---

25. Итоговая структура JSON-документа

Теперь можно сформулировать строго:

> JSON-документ формы состоит из трех обязательных блоков: meta, form, objects.
Блок meta хранит версию формата и тип документа.
Блок form хранит корневую форму (FormRoot) с полями id, type, name, root_widget_type, width, height, window_title.
Блок objects хранит плоский список всех сущностей формы, кроме корня.
Каждая сущность в objects обязана иметь поля id, type, parent_id, name, order, geometry, properties.
Вложенность определяется через parent_id, порядок через order, геометрия хранится в блоке geometry, а типозависимые свойства — в блоке properties.

26. Что дальше

Теперь у нас уже есть почти полный каркас внутреннего формата.

Следующий правильный шаг:

операции FormDocument

То есть нужно зафиксировать:

какие команды должна поддерживать модель документа

как добавляется объект

как удаляется поддерево

как меняется родитель

как добавляется страница у специальных контейнеров

как меняется порядок


Это уже следующий обязательный слой между JSON и живым редактором.



Продолжаю. Следующий обязательный слой — операции FormDocument.

Если JSON — это структура данных, то FormDocument — это живая модель, через которую редактор работает с этой структурой.

Именно FormDocument должен быть тем объектом, который умеет:

создавать сущности

удалять сущности

перемещать сущности

менять свойства

менять геометрию

управлять страницами контейнеров

проверять корректность структуры

отдавать данные на сериализацию


То есть редактор не должен “ковырять JSON руками”.
Он должен работать через понятный набор операций документа.


---

1. Что такое FormDocument

FormDocument — это центральная объектная модель формы в памяти.

Он существует после:

Создать

Загрузить


И до:

закрытия формы

создания нового документа

загрузки другого документа



---

2. За что отвечает FormDocument

Он отвечает за 5 вещей:

2.1. Хранение структуры формы

form

objects


2.2. Доступ к объектам

найти объект по id

получить детей

получить родителя

получить страницы контейнера


2.3. Изменение структуры

добавить

удалить

переместить

поменять порядок


2.4. Изменение данных

свойства

геометрия

имя

параметры страницы

текущие индексы контейнеров


2.5. Подготовка к сериализации

выдать корректное состояние документа

без временного UI-состояния



---

3. Принцип работы FormDocument

Все действия редактора должны идти через него.

То есть:

пользователь перетащил объект → вызывается операция документа

пользователь удалил объект → вызывается операция документа

пользователь поменял text → вызывается операция документа

пользователь добавил вкладку → вызывается операция документа


Это критично.


---

4. Что должно храниться внутри FormDocument

Логически внутри он должен содержать:

4.1. Корень формы

объект FormRoot


4.2. Коллекцию сущностей

Все объекты формы

4.3. Быстрый индекс по id

Чтобы не искать сущности линейно каждый раз

4.4. Возможно индекс по parent_id

Чтобы быстро получать детей


---

5. Представление в памяти

Для JSON у нас:

плоский список objects


Для FormDocument в памяти лучше так:

form_root

entities_by_id

функции для получения детей по parent_id



---

6. Набор обязательных операций FormDocument

Нужно разделить операции на группы.


---

7. Группа A — Чтение и навигация

Это базовые операции доступа.


---

7.1. get_form_root()

Возвращает FormRoot.

Зачем

Чтобы редактор мог получить:

размеры формы

тип корня

заголовок формы



---

7.2. get_entity(entity_id)

Возвращает сущность по id.

Зачем

Это одна из главных базовых операций.


---

7.3. has_entity(entity_id)

Проверяет, существует ли сущность.

Зачем

Для безопасных операций удаления, обновления и проверки ссылок.


---

7.4. get_parent(entity_id)

Возвращает родителя сущности.

Особенность

Если parent_id == form_root, родитель — это корень формы.


---

7.5. get_children(parent_id)

Возвращает прямых детей родителя.

Важно

Дети должны возвращаться в порядке order.


---

7.6. get_descendants(parent_id)

Возвращает все вложенные сущности поддерева.

Зачем

Нужно для:

удаления контейнера

клонирования

экспорта поддерева

анализа структуры



---

7.7. get_root_entities()

Возвращает все объекты верхнего уровня, у которых:

parent_id == form_root



---

8. Группа B — Создание сущностей

Это операции появления объектов.


---

8.1. create_entity(type, parent_id, geometry=None, properties=None, name=None)

Создает обычную сущность документа.

Что делает

генерирует id

определяет order

берет дефолтные параметры типа

подставляет переданные свойства

создает объект

помещает его в документ


Возвращает

entity_id



---

8.2. Почему создание должно идти через реестр типов

Потому что FormDocument сам не должен знать на уровне кода все дефолты каждого объекта.

Он должен опираться на:

реестр типов

дефолтные свойства

дефолтную геометрию

правила вложенности



---

8.3. create_entity_from_palette_drop(type, target_parent_id, drop_position)

Это уже более прикладная операция для редактора.

Что делает

определяет допустимого родителя

вычисляет локальные координаты

создает объект с дефолтной геометрией

возвращает созданную сущность



---

9. Группа C — Специальное создание контейнеров

Обычное создание здесь недостаточно.


---

10. create_tab_widget(parent_id, geometry, name=None)

Создает QTabWidget вместе с внутренней структурой.

Что делает

1. создает сам QTabWidget


2. создает минимум две TabPage


3. задает им порядок


4. ставит current_index = 0



Почему отдельная операция

Потому что простой create_entity("QTabWidget") не создает завершенный рабочий контейнер.


---

11. create_toolbox(parent_id, geometry, name=None)

Должен:

1. создать QToolBox


2. создать минимум две ToolPage




---

12. create_stacked_widget(parent_id, geometry, name=None)

Должен:

1. создать QStackedWidget


2. создать минимум две StackPage




---

13. create_scroll_area(parent_id, geometry, name=None)

Должен:

1. создать QScrollArea


2. создать ContainerContent


3. связать content с scroll area




---

14. create_splitter(parent_id, geometry, name=None, orientation="horizontal")

Должен:

1. создать QSplitter


2. создать внутренние панели/контейнеры splitter


3. выставить размеры панелей



Здесь нужно заранее решить, как именно моделируются внутренние панели splitter:

как обычные QWidget или

как специальная внутренняя сущность


Для нашей архитектуры практичнее использовать:

обычные внутренние QWidget-панели, создаваемые системой



---

15. create_wizard(parent_id, geometry, name=None)

Если поддерживаем QWizard:

1. создать QWizard


2. создать минимум две WizardPage




---

16. Группа D — Изменение свойств сущности


---

16.1. update_property(entity_id, property_name, value)

Меняет одно свойство в properties.

Примеры

text

title

checked

current_index



---

16.2. update_properties(entity_id, properties_dict)

Меняет сразу несколько свойств.

Зачем

Удобно для:

пакетных обновлений

диалогов настройки

вставки готовых наборов данных



---

16.3. rename_entity(entity_id, new_name)

Отдельная операция для name.

Почему отдельно

name лежит не в properties, а на верхнем уровне сущности.


---

17. Группа E — Изменение геометрии


---

17.1. update_geometry(entity_id, x, y, width, height)

Полностью заменяет геометрию.


---

17.2. move_entity(entity_id, new_x, new_y)

Меняет только координаты.


---

17.3. resize_entity(entity_id, new_width, new_height)

Меняет только размер.


---

17.4. Почему это нужно разделить

Потому что:

move и resize в редакторе происходят как отдельные операции

не всегда нужно менять все 4 значения сразу



---

18. Группа F — Перестройка структуры

Это одна из самых важных групп.


---

18.1. reparent_entity(entity_id, new_parent_id, new_x, new_y)

Перемещает объект в нового родителя.

Что делает

проверяет допустимость вложенности

меняет parent_id

пересчитывает локальные координаты

назначает новый order


Зачем

Это нужно для drag&drop между контейнерами.


---

18.2. set_order(entity_id, new_order)

Меняет порядок объекта среди siblings.


---

18.3. reorder_within_parent(entity_id, direction)

Упрощенная операция:

вверх / вниз или

влево / вправо для вкладок


Зачем

Нужна для кнопок порядка в панели свойств.


---

19. Группа G — Удаление


---

19.1. delete_entity(entity_id)

Удаляет сущность.

Что должно происходить

Если сущность leaf:

просто удаляется


Если контейнер:

удаляется все поддерево



---

19.2. delete_subtree(entity_id)

Можно сделать отдельной явной операцией, даже если delete_entity() ее использует внутри.

Что делает

находит всех потомков

удаляет их в корректном порядке

затем удаляет корневую сущность



---

19.3. Важное правило

Удаление страницы special-container должно идти не как обычное удаление, а через специальные операции контейнера.


---

20. Группа H — Специальные операции для page-based контейнеров

Это отдельный обязательный слой.


---

21. add_tab_page(tab_widget_id, title=None)

Добавляет новую вкладку в QTabWidget.

Что делает

создает новую TabPage

назначает parent_id = tab_widget_id

ставит следующий order

задает title

при необходимости делает ее активной



---

22. remove_tab_page(tab_page_id)

или лучше
remove_tab_page(tab_widget_id, page_id)

Что делает

удаляет вкладку

удаляет все дочерние объекты этой страницы

перестраивает order

корректирует current_index



---

23. rename_tab_page(tab_page_id, new_title)

Меняет title вкладки.


---

24. set_current_tab(tab_widget_id, index)

Меняет активную вкладку.


---

FormDocument

2.2. Уровень интерфейса

Показывает форму и дает пользователю с ней работать.

8. WidgetRegistry

---

4. MainEditorWindow

Это левое узкое окно редактора.


---

Его роль

Он не хранит форму и не строит ее сам.

Он только:

показывает кнопки

показывает палитру объектов

показывает панель свойств

показывает кнопку удаления

координирует действия пользователя



---

Что в нем должно быть

Сверху вниз:

Верхняя полоса

Создать

Загрузить

Сохранить


Палитра

список доступных объектов


Панель свойств

параметры выбранного объекта


Нижняя зона

Удалить объект



---

За что он НЕ отвечает

Он не должен:

хранить структуру формы

напрямую менять JSON

напрямую создавать QWidget на форме

сам определять вложенность


Он только отправляет команды дальше.


---

5. FormWindow

Это отдельное окно, которое открывается после Создать или Загрузить.


---

Его роль

Это внешний контейнер для визуальной формы.


---

Что в нем находится

Внутри него находится:

CanvasEditor


То есть FormWindow — это окно-хост для редактора формы.


---

За что он отвечает

открыть окно формы

показать заголовок окна

содержать CanvasEditor

закрываться вместе с документом или по сценарию пользователя



---

За что он НЕ отвечает

Он не должен:

сам хранить документ

сам менять свойства объектов

сам сериализовать форму



---

6. PalettePanel

Это блок со списком объектов.


---

Его роль

Показывать доступные типы объектов и запускать drag&drop.


---

Что он должен уметь

показывать сгруппированный список типов

поддерживать drag start

передавать тип объекта в canvas



---

Что он НЕ должен уметь

создавать объекты напрямую

решать, куда их можно поместить

менять документ

знать про parent-child логику


То есть палитра знает:

что перетаскивают но не знает:

куда и как это будет вставлено



---

7. PropertyPanel

Это блок свойств выбранного объекта.


---

Его роль

Показывать параметры выбранной сущности и отправлять изменения в документ.


---

Что он должен уметь

получать выбранный объект

строить UI полей по типу объекта

показывать:

основную информацию

геометрию

свойства

специальные действия контейнеров


отправлять изменения в контроллер



---

Что он НЕ должен делать

напрямую менять FormDocument

напрямую менять QWidget на форме

сам решать правила вложенности



---

8. CanvasEditor

Это ключевой визуальный модуль.


---

Его роль

Показывать содержимое формы и принимать мышиные действия пользователя.

Это не документ и не serializer.
Это именно:

визуальный редактор формы


---

Что он должен уметь

строить визуальные объекты на основе FormDocument

принимать drag&drop из палитры

выбирать объект кликом

двигать объект мышью

менять размер объекта мышью

определять, в какой контейнер попадает drop

отправлять команды в контроллер



---

Что он НЕ должен делать

сам менять JSON

сам решать, как выглядит документ

сам создавать ids

сам валидировать parent-child модель как источник истины



---

9. FormDocument

Это уже зафиксированная модель формы в памяти.


---

Его роль

Хранить нормализованное состояние формы и поддерживать операции над ней.


---

Что он умеет

хранить form

хранить objects

давать API операций

валидировать структуру

отдавать данные сериализатору



---

Чего он не умеет

не знает про drag mouse move

не знает про QWidget instances

не знает про видимость панели свойств

не знает про кнопки интерфейса



---

10. DocumentController

Это один из самых важных модулей.

Если не выделить его явно, логика размазывается между UI и документом.


---

Его роль

Быть посредником между:

MainEditorWindow

PropertyPanel

CanvasEditor

FormDocument

Serializer

Converter


То есть это центральный координатор.


---

Что он должен делать

создавать новый документ

загружать документ

сохранять документ

обрабатывать drag&drop команды

принимать команды панели свойств

принимать команды удаления

обновлять выбор

сообщать UI, что изменилось



---

Почему он нужен

Без него получится хаос:

часть логики в canvas

часть в panel

часть в main window

часть в serializer


Контроллер нужен, чтобы все пользовательские действия сходились в одну точку.


---

11. WidgetRegistry

Это реестр типов объектов.


---

Его роль

Хранить знания о типах.

Он должен знать:

какие типы доступны

как они называются в палитре

к какой категории относятся

их дефолтные параметры

их дефолтную геометрию

какие свойства у них есть

контейнер они или нет

leaf они или нет

special-container они или нет



---

Почему это нужно

Чтобы:

не зашивать знания о типах в 10 разных местах

не дублировать дефолты

не размазывать правила по коду



---

12. FormSerializer

Это модуль работы с JSON.


---

Его роль

Читать и писать нормализованный JSON-документ.


---

Что он делает

FormDocument -> dict/json

dict/json -> FormDocument



---

Что он НЕ делает

не строит QWidget

не делает Python-код

не решает, какой объект можно куда вкладывать



---

13. PythonConverter

Это отдельный модуль.


---

Его роль

Переводить:

FormDocument / JSON -> Python

Python -> JSON / FormDocument



---

Почему он должен быть отдельным

Потому что Python-представление — это уже другой формат.

Нельзя смешивать:

структуру документа

и генерацию Python



---

14. Связи между модулями

Теперь соберем всю картину.


---

15. Главный поток управления

Пользователь работает через UI, но все изменения должны идти по одной цепочке:

Пользовательское действие

→ UI-модуль
→ DocumentController
→ FormDocument
→ обновление UI
→ при необходимости обновление JSON-файла


---

16. Поток создания новой формы

Шаги

1. пользователь нажимает Создать


2. MainEditorWindow передает команду в DocumentController


3. DocumentController создает новый FormDocument


4. FormSerializer формирует начальный JSON


5. открывается FormWindow


6. CanvasEditor строит пустую форму по документу


7. PropertyPanel переходит в состояние без выбранного объекта




---

17. Поток загрузки формы

Шаги

1. пользователь нажимает Загрузить


2. MainEditorWindow передает команду в DocumentController


3. контроллер получает файл


4. если это JSON:

FormSerializer загружает его



5. если это Python:

PythonConverter переводит его в JSON / dict

затем создается FormDocument



6. открывается FormWindow


7. CanvasEditor строит форму из документа




---

18. Поток drag&drop из палитры

Шаги

1. пользователь тащит объект из PalettePanel


2. CanvasEditor принимает drop


3. CanvasEditor определяет target-зону


4. CanvasEditor сообщает DocumentController:

тип объекта

целевого родителя

позицию drop



5. DocumentController вызывает создание в FormDocument


6. документ создает сущность


7. CanvasEditor обновляет отображение


8. PropertyPanel показывает созданный объект


9. FormSerializer при необходимости обновляет промежуточный файл




---

19. Поток выбора объекта

Шаги

1. пользователь кликает объект на форме


2. CanvasEditor определяет entity_id


3. передает выбор в DocumentController


4. контроллер делает этот объект активным в состоянии редактора


5. PropertyPanel получает сущность и строит UI свойств


6. CanvasEditor обновляет визуальное выделение




---

20. Поток редактирования свойств

Шаги

1. пользователь меняет поле в PropertyPanel


2. PropertyPanel не меняет документ сам, а отправляет команду в DocumentController


3. DocumentController вызывает:

rename_entity

update_property

update_geometry и т.д.



4. FormDocument обновляет данные


5. CanvasEditor получает сигнал / событие обновления


6. на форме обновляется соответствующий объект


7. промежуточный JSON обновляется




---

21. Поток перемещения объекта мышью

Шаги

1. пользователь тащит объект в CanvasEditor


2. во время движения canvas только показывает визуальное перемещение


3. после отпускания мыши:

CanvasEditor вычисляет финальную позицию

если нужно — нового родителя



4. передает это в DocumentController


5. контроллер вызывает:

move_entity или

reparent_entity



6. FormDocument обновляется


7. JSON обновляется




---

22. Поток resize объекта

Логика аналогична перемещению.

После завершения resize:

canvas передает размеры в контроллер

контроллер меняет геометрию в документе

документ обновляется

файл обновляется



---

23. Поток удаления объекта

Шаги

1. пользователь нажимает Del или кнопку удаления


2. команда идет в DocumentController


3. контроллер проверяет, что объект выбран


4. вызывает delete_entity / специальную delete-операцию


5. FormDocument удаляет сущность и поддерево


6. CanvasEditor перестраивает отображение


7. PropertyPanel очищается


8. JSON обновляется




---

24. Поток специальных операций контейнеров

Например: добавить вкладку.

Шаги

1. пользователь нажимает “Добавить вкладку” в PropertyPanel


2. PropertyPanel передает команду в DocumentController


3. контроллер вызывает:

add_tab_page



4. FormDocument создает TabPage


5. CanvasEditor обновляет QTabWidget


6. PropertyPanel обновляет список вкладок


7. файл обновляется



То же самое для:

toolbox

stacked

wizard

splitter



---

25. Где должно храниться текущее состояние выбора

Это не часть FormDocument.

Лучше хранить его в слое управления, например в DocumentController.


---

Что туда входит

selected_entity_id

возможно active_form_window

возможно active_container_context



---

26. Почему состояние выбора нельзя класть в документ

Потому что:

это не часть самой формы

это состояние редактора

при сохранении формы его не нужно писать в JSON



---

27. Кто инициирует обновление промежуточного файла

Здесь есть два варианта:

Вариант A

Каждый UI-модуль сам пишет файл
→ плохо

Вариант B

Контроллер централизованно инициирует обновление
→ правильно


---

Правильный вариант

После завершения операции DocumentController помечает документ измененным и запускает сохранение промежуточного JSON через FormSerializer.


---

28. Значит DocumentController должен уметь работать с dirty-state

Да.

Он должен:

получать от документа факт изменений

отслеживать dirty-state

запускать отложенную или немедленную запись JSON

вызывать экспорт в Python по кнопке Сохранить



---

29. Где граница между CanvasEditor и WidgetFactory

Нужен еще один важный вспомогательный модуль.


---

30. WidgetFactory

Его стоит выделить отдельно.


---

Его роль

Создавать реальные PySide6-объекты по данным сущности документа.


---

Что он делает

Например, если в документе есть:

type = QPushButton

properties.text = "Save"


то factory должен создать:

реальный QPushButton

применить геометрию

применить свойства



---

Почему это нужно отдельно

Потому что иначе CanvasEditor превратится в огромный перегруженный модуль.


---

31. Значит CanvasEditor работает не напрямую с типами, а через factory

35. Главный архитектурный принцип всей программы

Теперь его можно сформулировать очень четко:

> UI-модули не меняют форму напрямую.
Все пользовательские действия проходят через DocumentController, который вызывает операции FormDocument.
CanvasEditor только показывает документ и преобразует мышиные действия в команды.
PropertyPanel только показывает свойства и отправляет изменения.
FormSerializer и PythonConverter не содержат UI-логики.
Истина о форме всегда находится в FormDocument.

36. Что дальше

Теперь уже логично переходить к следующему обязательному слою:

реестр типов (WidgetRegistry)

Потому что именно он должен формализовать:

какие объекты поддерживаются

какие у них свойства

какие дефолты

leaf/container/special

допустимые родители

дефолтные размеры

специальные операции


Это следующий слой, который связывает:

список объектов

документ

canvas

panel

factory


И без него система будет дублировать знания о типах в разных местах.



Продолжаю. Следующий обязательный слой — WidgetRegistry, реестр типов объектов.

Это один из самых важных модулей, потому что именно он убирает хаос и дублирование знаний по системе.

Если его не сделать, информация о типах расползется по разным местам:

часть в PalettePanel

часть в PropertyPanel

часть в CanvasEditor

часть в FormDocument

часть в WidgetFactory

часть в PythonConverter


Это быстро сломает архитектуру.


---

1. Что такое WidgetRegistry

WidgetRegistry — это единый каталог знаний о поддерживаемых типах объектов.

Он должен отвечать на вопросы:

существует ли такой тип в системе

как он называется

к какой категории относится

можно ли его брать из палитры

leaf это или container

special-container это или нет

какие у него свойства

какие у него дефолтные значения

какие у него дефолтные размеры

где его можно размещать

есть ли у него специальные операции

как его строить в UI

как его сериализовать

как его генерировать в Python


То есть это не просто список классов, а официальное описание типа в редакторе.


---

2. Главная роль WidgetRegistry

Нужно зафиксировать один принцип:

> WidgetRegistry — это не хранилище экземпляров объектов, а хранилище описаний типов



Он не хранит:

конкретные кнопки

конкретные поля

конкретные страницы


Он хранит:

описание QPushButton

описание QTabWidget

описание TabPage

описание QScrollArea



---

3. Почему реестр обязателен

Он нужен сразу по нескольким причинам.


---

4. Причина 1 — единый список поддерживаемых типов

Система должна знать точно:

какие типы поддерживаются

какие не поддерживаются


И это нельзя держать “по памяти” в разных модулях.


---

5. Причина 2 — дефолты

Когда пользователь бросает объект на форму, нужно сразу знать:

какую ширину дать

какую высоту дать

какое имя предложить

какие свойства создать

какие значения поставить по умолчанию


Это все должно идти из реестра.


---

6. Причина 3 — правила отображения в палитре

Палитра должна понимать:

что показывать пользователю

как группировать объекты

что скрыто

что является внутренней сущностью и не попадает в палитру


Это тоже должен определять реестр.


---

7. Причина 4 — панель свойств

Панель свойств должна понимать:

какие поля показывать для данного типа

какой редактор использовать для свойства

какие значения допустимы


Эти знания нельзя вручную зашивать в десятке if по всему приложению.


---

8. Причина 5 — WidgetFactory

Когда CanvasEditor хочет построить визуальный объект, нужен ответ на вопрос:

какой реальный PySide6-класс создавать

как применять свойства

есть ли особенности создания


И это тоже должно идти из реестра типов.


---

9. Причина 6 — FormDocument

Документ должен понимать:

допустим ли тип

допустим ли родитель

дефолтные свойства

особый ли это контейнер


Но сам документ не должен тащить в себе огромный список знаний.
Он должен обращаться к реестру.


---

10. Что должно храниться в WidgetRegistry

Теперь фиксируем состав описания типа.

У каждого типа в реестре должен быть type definition — описание типа.


---

11. Что должно быть в описании типа

У каждого объекта реестра должны быть следующие блоки.


---

12. Блок 1 — идентификация типа

Это базовая информация.


---

12.1. type_name

Например:

QPushButton

QTabWidget

TabPage


Назначение

Официальное имя типа в системе.


---

12.2. display_name

Например:

Button

Tab Widget

Tab Page


Назначение

Имя, которое можно показывать пользователю в палитре и панели.


---

12.3. category

Например:

text_input

selection

container

pages

data_view


Назначение

Группировка в палитре и общей логике UI.


---

13. Блок 2 — роль типа в редакторе

Это очень важный слой.


---

13.1. editor_kind

Тип редакторского поведения.

Нужно зафиксировать допустимые значения:

leaf

container

special_container

internal



---

Что они означают

leaf

Обычный объект без детей

container

Обычный контейнер с прямыми детьми

special_container

Контейнер со специальной внутренней структурой

internal

Внутренняя сущность, не попадает в палитру


---

13.2. Примеры

QPushButton → leaf

QGroupBox → container

QTabWidget → special_container

TabPage → internal



---

14. Блок 3 — доступность в палитре


---

14.1. palette_visible

Тип: bool

Назначение

Показывать ли объект в палитре пользователю.

Примеры

QPushButton → true

TabPage → false

ContainerContent → false



---

14.2. palette_group

Тип: str

Назначение

Группа палитры.

Примеры:

Text and Input

Selection

Containers

Pages

Data Views



---

15. Блок 4 — дефолтная геометрия

Это обязательный слой.


---

15.1. default_size

Тип: dict

Содержит:

width

height


Пример

{
  "width": 120,
  "height": 32
}


---

15.2. Почему это нужно

Когда объект падает на форму, ему сразу нужен разумный размер.


---

16. Блок 5 — дефолтное имя


---

16.1. name_prefix

Тип: str

Примеры

label

push_button

group_box

tab_widget


Назначение

Используется для автоматической генерации name.

Например:

push_button_1

group_box_3



---

17. Блок 6 — свойства типа

Это ключевой слой.


---

17.1. property_schema

Тип: dict

Это описание всех поддерживаемых свойств данного типа.


---

17.2. Для каждого свойства нужно хранить:

имя свойства

тип данных

обязательность

значение по умолчанию

допустимые значения, если они ограничены

тип редактора для панели свойств



---

17.3. Пример для QPushButton

{
  "text": {
    "data_type": "str",
    "required": true,
    "default": "Button",
    "editor": "text"
  }
}


---

18. Блок 7 — правила вложенности

Это тоже должно жить в реестре.


---

18.1. allowed_parent_types

Тип: list[str] | "*"

Назначение

Какие родители допустимы для данного типа.

Примеры:

QPushButton → ["FormRoot", "QWidget", "QFrame", "QGroupBox", "TabPage", "ToolPage", "StackPage", "WizardPage", "ContainerContent"]

TabPage → ["QTabWidget"]



---

18.2. allowed_child_types

Тип: list[str] | None

Назначение

Какие типы детей допустимы внутри этого объекта.

Примеры:

QLabel → None

QGroupBox → список допустимых детей

QTabWidget → ["TabPage"]



---

18.3. direct_children_only

Тип: bool

Назначение

Показывает, что этот объект принимает только строго определенные прямые дочерние типы.

Полезно для:

QTabWidget

QToolBox

QStackedWidget

QWizard

QScrollArea



---

19. Блок 8 — специальные операции типа

Некоторые объекты требуют специальных действий.


---

19.1. special_actions

Тип: list[str]

Примеры

Для QTabWidget:

add_tab_page

remove_tab_page

rename_tab_page

set_current_tab


Для QSplitter:

add_splitter_panel

remove_splitter_panel

set_splitter_sizes


Для QScrollArea:

get_scroll_content



---

20. Блок 9 — автоматическое создание внутренних сущностей

Это критично для special-container типов.


---

20.1. auto_create_children

Тип: list[dict]

Назначение

Какие внутренние сущности автоматически создаются вместе с этим типом.


---

20.2. Примеры

QTabWidget

создает минимум две TabPage


QScrollArea

создает ContainerContent


QSplitter

создает две внутренние панели



---

21. Блок 10 — визуальная фабрика

Нужно ли реестру знать, какой Qt-класс создавать?

Да, но аккуратно.


---

21.1. qt_class_name

Тип: str | None

Примеры

QPushButton → QPushButton

TabPage → QWidget или специальная внутренняя обертка

ContainerContent → QWidget


Назначение

Помогает WidgetFactory понимать, что реально создавать.


---

22. Блок 11 — режим редактирования геометрии

Это полезно хранить в реестре.


---

22.1. geometry_edit_mode

Тип: str

Допустимые значения:

full

readonly

hidden



---

Значение

full

Показывать и редактировать x, y, width, height

readonly

Показывать, но не редактировать

hidden

Не показывать в панели свойств


---

22.2. Примеры

QPushButton → full

TabPage → readonly или hidden

ContainerContent → hidden



---

23. Блок 12 — возможность resize и move

Это тоже лучше хранить в типовом описании.


---

23.1. movable

Тип: bool

Назначение

Можно ли двигать объект как свободный объект мышью.


---

23.2. resizable

Тип: bool

Назначение

Можно ли менять размер мышью.


---

23.3. Примеры

QPushButton → movable=true, resizable=true

TabPage → movable=false, resizable=false

ContainerContent → movable=false, resizable=false



---

24. Блок 13 — возможность прямого удаления


---

24.1. deletable_directly

Тип: bool

Назначение

Можно ли удалить объект напрямую как обычную сущность.


---

24.2. Примеры

QPushButton → true

QGroupBox → true

TabPage → false

WizardPage → false

ContainerContent → false



---

25. Блок 14 — можно ли создавать из палитры

palette_visible=true уже почти это покрывает, но полезно иметь более явное поле.


---

25.1. creatable_by_user

Тип: bool

Примеры

QPushButton → true

TabPage → false

ContainerContent → false



---

26. Итоговая модель описания типа

Теперь можно сформулировать:

> описание типа в WidgetRegistry должно содержать идентификацию типа, роль в редакторе, доступность в палитре, дефолтную геометрию, схему свойств, правила вложенности, специальные действия, правила автоматического создания внутренних сущностей, визуальный Qt-класс и ограничения редактирования.

31. Как WidgetRegistry должен использоваться в системе

Теперь главное — где он нужен.


---

32. Использование в PalettePanel

Палитра должна запрашивать у реестра:

все типы, где palette_visible = true

их группы

display name


Палитра не должна сама хранить список объектов.


---

33. Использование в PropertyPanel

Панель свойств должна брать из реестра:

property_schema

geometry_edit_mode

тип редактора поля

допустимые значения


То есть панель свойств не должна знать свойства по if-цепочкам.


---

34. Использование в CanvasEditor

Canvas должен брать из реестра:

movable / resizable

editor_kind

special-container behavior hints



---

35. Использование в WidgetFactory

Factory должен брать из реестра:

qt_class_name

default properties

schema properties



---

36. Использование в FormDocument

Документ должен брать из реестра:

дефолтные размеры

дефолтные свойства

правила parent-child

special actions

auto-create rules



---

37. Использование в PythonConverter

Конвертер должен брать из реестра:

mapping на Qt-класс

supported properties

page/container rules



---

38. Нужен ли WidgetRegistry в виде кода или данных

Лучше всего строить его как данные, а не как размазанный код.

То есть:

либо Python-словарь со схемами

либо отдельные dataclass-описания типов

либо JSON/YAML-конфиг, если захочется вынести наружу


Для текущей архитектуры наиболее практично:

держать его как Python-описания типов внутри приложения



---

39. Нужна ли иерархия наследования описаний

Например:

базовый тип InputWidget

от него ComboBox

от него FontComboBox


На текущем этапе — не обязательно.

Это может усложнить систему.

Практичнее:

явные записи типов

при необходимости утилиты для генерации похожих схем



---

40. Главный итог по WidgetRegistry

Теперь можно сформулировать строго:

1. Главный принцип визуального слоя

Нужно сразу зафиксировать:

> пользователь работает не с “голым” QPushButton или QLineEdit, а с редакторским представлением объекта



Это значит, что на canvas должен существовать не просто Qt-виджет, а:

визуальная сущность редактора

которая содержит:

сам внутренний Qt-объект

2. Почему нельзя опираться только на чистые Qt-виджеты

Если использовать на canvas только реальные Qt-виджеты без оболочки, сразу появятся проблемы:

у разных виджетов разное мышиное поведение

сложно выделять контейнеры и листовые объекты одинаково

сложно рисовать рамку выделения

сложно ловить resize одинаково для всех

сложно обеспечить единый UX


Поэтому нужен промежуточный слой.

3. Значит у визуальной части должны быть два уровня

3.1. Внутренний уровень

Реальный PySide6-виджет:

QPushButton

QGroupBox

QTabWidget и т.д.


3.2. Внешний уровень

Редакторская оболочка:

знает entity_id

умеет выделяться

умеет двигаться

умеет ресайзиться

умеет сообщать canvas, что по ней кликнули

4. Нужна ли единая оболочка для всех объектов

Это не название для пользователя, а внутренняя архитектурная сущность.

5. Что такое FormItemView

FormItemView — это редакторская визуальная обертка одной сущности документа.

Он должен быть связан с одной сущностью FormDocument.


---

У него есть:

внутренний созданный Qt-виджет

состояние выделения

состояние resize

связь с canvas

возможность обновить свой вид по документу



---

6. Главная роль FormItemView

Он должен уметь:

построить визуальное представление объекта

отрисовать его на canvas

выделяться

передвигаться

менять размер

принимать события мыши

сообщать canvas, что произошло действие

7. Что НЕ должен делать FormItemView

Он не должен:

сам менять FormDocument

То есть он:

показывает

ловит действия

делегирует изменения наверх

8. Теперь роль WidgetFactory

WidgetFactory отвечает за другое.

Он должен уметь:

> по сущности документа создать правильный внутренний Qt-виджет и применить к нему свойства



То есть factory — это:

документ → Qt-объект

10. Пример этой границы

21. Выделение объекта

Это нужно зафиксировать отдельно, потому что это важный UX.

Как должно выглядеть выделение

Когда объект выбран:

вокруг него появляется рамка

появляются resize-handles

выбранность видна однозначно



---

Где должна рисоваться рамка

Не внутренним Qt-виджетом, а оболочкой FormItemView.

Потому что:

нельзя полагаться на стиль самого виджета

надо одинаково показывать выделение у всех типов

22. Resize-handles

Это тоже обязанность редакторской оболочки.


---

Что это такое

Маленькие маркеры по углам и/или сторонам объекта.


---

Что они дают

Пользователь тянет за них и меняет размер объекта.


---

Где они существуют

На уровне FormItemView, не на уровне Qt-виджета.

23. Drag move

При перемещении объекта:

FormItemView отслеживает мышь

показывает живое движение

canvas понимает потенциальный target-parent

по завершении отправляется команда в контроллер



---

24. Важно: живое перемещение не должно сразу править документ

Во время движения:

меняется только визуальное представление


После отпускания мыши:

вычисляется финальная позиция

отправляется операция в DocumentController

тот обновляет FormDocument


Это сохраняет правильную архитектуру.


---

25. То же самое для resize

Во время resize:

меняется только визуальная рамка / размер оболочки


После завершения:

обновляется FormDocument

Canvas не должен работать напрямую с каждым QPushButton.

1. Общий жизненный цикл формы

У формы в программе есть 8 основных состояний:

1. программа запущена, формы нет


2. создается новый документ


3. или загружается существующий документ


4. открывается окно формы


5. пользователь редактирует форму


6. документ синхронизируется в JSON


7. по команде создается Python


8. форма закрывается




---

2. Состояние 1 — программа запущена, формы нет

Это первое состояние после старта приложения.


---

Что существует

MainEditorWindow

PalettePanel

пустая PropertyPanel

верхние кнопки управления



---

Что не существует

активный FormDocument

FormWindow

CanvasEditor с документом

промежуточный файл формы

выбранный объект



---

Что пользователь может делать

нажать Создать

нажать Загрузить


Все остальное должно быть неактивным или пустым.


---

3. Состояние 2 — создание новой формы

Это сценарий по кнопке Создать.


---

3.1. Что запускает пользователь

Нажимает Создать.


---

3.2. Что делает MainEditorWindow

Передает команду в DocumentController.


---

3.3. Что делает DocumentController

Он должен:

1. создать новый FormDocument


2. создать FormRoot с дефолтными значениями


3. подготовить начальный JSON-документ


4. открыть новое FormWindow


5. связать это окно с новым документом




---

3.4. Что происходит с документом

Создается новый документ в памяти:

meta

form

пустой objects



---

3.5. Что происходит с JSON

Сразу создается промежуточное состояние формы.

Это может быть:

уже созданный физический файл или

подготовленный документ в памяти, который сразу привязывается к будущему файлу


Но с учетом нашей договоренности правильнее:

форма живет через промежуточный документ сразу



---

3.6. Что происходит с окном формы

Открывается отдельное FormWindow.

Внутри него:

создается CanvasEditor

canvas получает пустой FormDocument

строится пустая форма



---

3.7. Что видит пользователь

слева остается главное окно

отдельно открывается пустая форма

свойства пустые

можно начинать drag&drop



---

4. Состояние 3 — загрузка существующей формы

Это сценарий по кнопке Загрузить.


---

4.1. Что запускает пользователь

Нажимает Загрузить и выбирает файл.


---

4.2. Что делает DocumentController

Он определяет тип файла:

JSON

Python



---

4.3. Если это JSON

1. FormSerializer читает файл


2. создает FormDocument


3. валидирует структуру


4. открывает FormWindow


5. canvas строит визуальную форму по документу




---

4.4. Если это Python

1. PythonConverter читает Python


2. извлекает структуру формы


3. преобразует в нормализованный dict / JSON-вид


4. создается FormDocument


5. открывается FormWindow


6. форма строится на canvas




---

4.5. Что важно

После загрузки, независимо от исходного формата:

активным рабочим состоянием становится именно FormDocument

дальше все редактирование идет уже через него



---

5. Состояние 4 — форма открыта, но объект не выбран

Это первое рабочее состояние после создания или загрузки.


---

Что существует

MainEditorWindow

FormWindow

CanvasEditor

активный FormDocument



---

Что на canvas

форма визуально построена

все объекты отображены

ничего не выделено



---

Что в панели свойств

Есть два допустимых варианта:

Вариант A

Пустая панель с надписью:

“Объект не выбран”


Вариант B

Показываются свойства самой формы:

name

root_widget_type

width

height

window_title


Для нашей системы вариант B полезнее.

6. Состояние 5 — добавление нового объекта

Это один из основных пользовательских сценариев.


---

6.1. Что делает пользователь

берет объект из палитры

тащит его на форму

отпускает в допустимой области



---

6.2. Что делает PalettePanel

Только инициирует drag и передает тип объекта.


---

6.3. Что делает CanvasEditor

Во время drag-over он:

определяет потенциальный target-parent

подсвечивает допустимую область вставки

показывает, можно ли сюда бросать объект



---

6.4. Что происходит в момент drop

CanvasEditor получает:

тип объекта

точку drop

целевую область


и передает это в DocumentController.


---

6.5. Что делает DocumentController

Он:

1. проверяет допустимость вложенности


2. выбирает нужную операцию:

обычное create_entity

специальное создание контейнера



3. создает сущность в FormDocument


4. помечает документ dirty


5. сообщает canvas, что нужно отобразить новый объект


6. делает этот объект выбранным




---

6.6. Что делает CanvasEditor после этого

создает FormItemView

через WidgetFactory строит внутренний Qt-объект

размещает его

показывает выделение



---

6.7. Что делает PropertyPanel

Получает новый выбранный объект и показывает его свойства.


---

6.8. Что происходит с JSON

После завершенной операции создания:

промежуточный JSON обновляется



---

7. Состояние 6 — выбор объекта


---

7.1. Что делает пользователь

Кликает по объекту на форме.


---

7.2. Что делает CanvasEditor

определяет entity_id

передает событие в DocumentController



---

7.3. Что делает DocumentController

обновляет selected state редактора

сообщает canvas обновить выделение

сообщает PropertyPanel построить панель для выбранной сущности



---

7.4. Что видит пользователь

рамка вокруг объекта

свойства этого объекта слева



---

8. Состояние 7 — перемещение объекта


---

8.1. Что делает пользователь

берет объект мышью

двигает его

отпускает



---

8.2. Что делает FormItemView

показывает живое перемещение

не пишет ничего в документ немедленно



---

8.3. Что делает CanvasEditor

Во время движения:

отслеживает потенциального нового родителя

показывает допустимую зону

может подсвечивать контейнер, куда объект попадет



---

8.4. После отпускания мыши

CanvasEditor передает в DocumentController:

entity_id

новую геометрию

нового родителя, если он изменился



---

8.5. Что делает DocumentController

Если родитель не изменился:

вызывает move_entity(...)


Если родитель изменился:

вызывает reparent_entity(...)



---

8.6. Что делает FormDocument

обновляет x, y

при необходимости parent_id

при необходимости order



---

8.7. Что происходит далее

canvas обновляет положение

property panel показывает новые координаты

JSON обновляется

9. Состояние 8 — изменение размера объекта


---

9.1. Что делает пользователь

Тянет resize-handle.


---

9.2. Что делает FormItemView

показывает живое изменение размера



---

9.3. После завершения resize

CanvasEditor передает финальную геометрию в DocumentController.


---

9.4. Что делает контроллер

Вызывает:

---

9.5. Что происходит далее

обновляется документ

обновляется JSON

property panel показывает новые размеры

12. Сценарий QTabWidget


---

Создание

Пользователь бросает QTabWidget.

Контроллер вызывает:

create_tab_widget(...)


Документ создает:

сам QTabWidget

минимум две TabPage


Canvas строит:

вкладки

первую активную страницу



---

Добавление вкладки

Пользователь нажимает “Добавить вкладку” в панели свойств.

Контроллер вызывает:

add_tab_page(...)


Документ создает новую TabPage.

Canvas обновляет QTabWidget.


---

Переименование вкладки

Через PropertyPanel.

Контроллер вызывает:

rename_tab_page(...)


Документ меняет properties.title у нужной TabPage.

Canvas обновляет заголовок вкладки.


---

Удаление вкладки

Контроллер вызывает:

remove_tab_page(...)


Документ:

удаляет TabPage

удаляет все дочерние объекты этой страницы

перестраивает order

корректирует current_index


Canvas обновляет tabs.


---

Drop объекта во вкладку

Canvas понимает, какая вкладка активна, и передает в документ:

parent_id = нужная TabPage



---

18. Состояние 12 — автосинхронизация промежуточного JSON

Это отдельный жизненный сценарий, но он должен быть встроен во все операции.


---

Когда документ становится dirty

После любой завершенной операции:

создание

удаление

move

resize

property change

add/remove page

reorder



---

Что делает контроллер

помечает документ как измененный

запускает обновление промежуточного JSON



---

Когда именно писать JSON

С учетом нашей договоренности:

не на каждый пиксель мыши

а после завершения действия


То есть после:

drop

mouse release после move

mouse release после resize

завершенного изменения свойства

19. Состояние 13 — сохранение в Python


---

Что делает пользователь

Нажимает Сохранить.


---

Что делает MainEditorWindow

Передает команду в DocumentController.


---

Что делает DocumentController

1. получает актуальный FormDocument


2. убеждается, что JSON-состояние актуально


3. передает документ в PythonConverter




---

Что делает PythonConverter

строит Python-представление формы

создает .py файл

Сохранить не должно означать:

21. Состояние 15 — закрытие окна формы

Это тоже обязательный сценарий.


---

Что делает пользователь

Закрывает FormWindow.


---

Что должна сделать система

Если документ dirty:

предупредить, что есть несохраненный экспорт в Python, если это действительно нужно по UX

или просто закрыть, если промежуточный JSON уже всегда актуален

В нашей архитектуре

Поскольку промежуточный JSON уже поддерживается в актуальном состоянии, закрытие формы не опасно с точки зрения потери модели.

Но можно отдельно решать:

предупреждать ли об отсутствии сохраненного Python

22. Что происходит после закрытия формы

23. Возможность нескольких форм одновременно

Теперь важный вопрос.


---

Нужна ли многодокументность

С учетом текущей постановки разумнее:

один активный документ за раз


То есть:

одно левое окно редактора

одно активное окно формы



---

Почему

Это сильно упрощает:

выбор объекта

панель свойств

контроллер

dirty-state

синхронизацию


Если later понадобится, многодокументность можно добавить, но сейчас лучше не закладывать как обязательную.

25. Полная последовательность

1. Старт программы

Открыто только левое окно редактора.

2. Создание или загрузка формы

Появляется активный FormDocument.

3. Открытие FormWindow

Canvas строит форму из документа.

4. Пользователь работает мышью

Добавляет, выбирает, двигает, меняет размер.

5. Пользователь меняет свойства

Через PropertyPanel.

6. Все действия идут через DocumentController

Он меняет FormDocument.

7. CanvasEditor обновляет визуальное представление

По изменениям документа.

8. Промежуточный JSON обновляется

После завершенных действий.

9. По кнопке Сохранить

PythonConverter создает .py.

10. При закрытии формы

Окно формы закрывается, главное окно остается.


---

26. Главный системный принцип жизненного цикла

Теперь уже можно сформулировать окончательно:

> пользователь работает не напрямую с виджетами и не напрямую с JSON.
Он работает с визуальным окном формы.
Все его действия попадают в DocumentController, который меняет FormDocument.
CanvasEditor отображает документ, PropertyPanel редактирует выбранную сущность, FormSerializer поддерживает актуальный промежуточный JSON, а PythonConverter по команде формирует итоговый Python-файл.

1. Главный принцип модульной схемы

Нужно жестко зафиксировать архитектурное правило:

> каждый модуль отвечает только за свой слой, не дублирует чужую ответственность и не знает лишнего



То есть:

UI не хранит истину о форме

документ не знает про мышь и окна

serializer не знает про canvas

converter не знает про selection

palette не знает про parent-child

property panel не знает, как создавать Qt-виджеты

4. ui editor — окно редактора, палитра, свойства

---

1. Назначение конструктора

Конструктор — это универсальный визуальный редактор форм на базе PySide6.

Его задача:

позволять создавать и редактировать формы мышью

собирать форму из реальных объектов PySide6

размещать объекты на форме

менять их размеры и свойства

поддерживать контейнеры, страницы, вкладки и сложные структуры

сохранять рабочее состояние формы в промежуточный JSON-документ

экспортировать итог формы в Python-файл


Это не Qt Designer общего назначения и не конструктор всего приложения.
Это именно редактор форм, заточенный под:

практичную работу мышью

простую и понятную структуру

модульную архитектуру

возможность применения в разных проектах



---

2. Общий принцип существования системы

Система строится вокруг одного главного принципа:

> истина о форме всегда находится в FormDocument



Это означает:

форма не хранится в палитре

форма не хранится в canvas

форма не хранится в панели свойств

форма не хранится в реальных QWidget как источнике истины


Истина о форме существует только как:

корень формы FormRoot

список сущностей документа

их параметры

их связи

их геометрия

их свойства


Все остальное — визуализация и управление.


---

3. Общий пользовательский сценарий

Пользователь работает так:

1. запускает редактор


2. видит только левое узкое окно управления


3. нажимает Создать или Загрузить


4. открывается отдельное окно формы


5. перетаскивает объекты из палитры на форму


6. двигает их и меняет размер мышью


7. выбирает объект кликом


8. меняет его свойства в панели свойств


9. удаляет объект при необходимости


10. сохраняет итог в Python

12. Поведение объектов в редакторе


---

12.1. Leaf-объекты

берутся из палитры

добавляются drag&drop

двигаются

меняют размер

выбираются

удаляются напрямую



---

12.2. Обычные контейнеры

берутся из палитры

добавляются drag&drop

двигаются

меняют размер

принимают дочерние объекты

удаляются вместе с поддеревом



---

12.3. Специальные контейнеры

берутся из палитры

создаются как сложные структуры

имеют специальные операции

содержат внутренние страницы или области

удаляются вместе со всей внутренней структурой



---

12.4. Внутренние страницы

не берутся из палитры

создаются автоматически

не двигаются как свободные объекты

удаляются только через родительский контейнер

23. Главные архитектурные правила

Это финальные правила системы.


---

23.1.

Истина о форме только в FormDocument.

23.2.

UI-модули не меняют документ напрямую.

23.3.

Все действия пользователя проходят через DocumentController.

23.4.

Типы объектов описываются только через WidgetRegistry.

23.5.

Canvas показывает документ, но не является его источником истины.

23.6.

JSON — канонический внутренний рабочий формат.

23.7.

Python — итоговый экспортный формат.

23.8.

Внутренние страницы и служебные области — реальные сущности модели, но не объекты палитры.

23.9.

Вложенность определяется только через parent_id.

23.10.

Порядок siblings определяется только через order.

1. Зачем нужна фиксация структуры проекта

Если сразу начать писать файлы без структуры, быстро появится типичная проблема:

часть логики в одном файле

UI и модель смешаны

serializer знает про canvas

palette знает про document

специальные контейнеры размазаны по разным местам


Поэтому нужно заранее определить:

какие папки есть

какие файлы в них лежат

какие классы где живут

что считается ядром

что считается UI

что считается инфраструктурой



---

2. Главный принцип структуры проекта

Нужно строить проект по ответственности, а не “по экрану” и не “по виджету”.

То есть правильно делить на:

модель

реестр типов

контроллер

визуальный слой

сериализацию

конвертацию

UI-оболочку

1. Зачем фиксировать порядок реализации

Даже при правильной архитектуре проект легко разваливается, если собирать его не в том порядке.

Типичные ошибки:

пытаться сразу строить canvas до документа

делать property panel до registry

делать Python exporter до стабильной JSON-модели

делать special-container UI до базовой модели сущностей

распараллеливать слои, которые еще не имеют опоры


Поэтому нужен жесткий принцип:

> сначала строятся фундаментальные слои, потом связующие, потом визуальные, потом специальные режимы, потом экспорт




---

2. Главный принцип этапности

Порядок должен идти от истины формы к визуальному интерфейсу, а не наоборот.

То есть:

1. модель


2. реестр типов


3. документ


4. сериализация


5. контроллер


6. базовый UI


7. canvas

9. экспорт Python



Это правильная последовательность.

---

QStackedWidget

После tab widget легче добавить еще один page-based контейнер, но уже без видимых вкладок.


---

QToolBox

Похож на page-based контейнер, но с другой визуальной оболочкой.


---

QSplitter

Сложнее из-за внутренних панелей и деления области.


---

Лучше в конце, потому что это наименее базовый сценарий.

Потому что Python exporter должен опираться на уже стабильную:

special-container правила


Если делать exporter раньше, придется потом его постоянно ломать и переписывать.

Сделать рабочий PythonExporter.

генерация QWidget-формы

генерация QDialog-формы

генерация объектов по дереву документа

генерация special-container структур

генерация geometry

генерация свойств



---

Что должно заработать

Пользователь нажимает Сохранить → получает валидный .py, который строит форму.
