Четырнадцатая рабочая контрольная точка

Собери финальную стабилизацию конструктора.

Закрой строго это состояние:

все уже реализованные модули работают согласованно

нет дублирующих путей изменения документа

selection logic стабильна

delete/rebuild сценарии не ломают состояние

create/load/save/export/import работают как единый цикл

canvas, property panel и JSON snapshot всегда синхронизированы

special-container типы работают по единым правилам

архитектура приведена к минимально-достаточной итоговой версии без лишних функций


После этого считай конструктор архитектурно закрытым.


---

1. Цель финальной стабилизации

Не добавляй новые сущности и новые режимы.
Доведи до устойчивости уже собранное.

Задача этапа:

убрать слабые места

убрать временные обходы

выровнять поведение системы

зафиксировать итоговую рабочую версию



---

2. Проведи ревизию источника истины

Проверь и зафиксируй окончательно:

Истина о форме только в FormDocument

Убедись, что:

CanvasEditor не хранит собственную независимую модель формы

PropertyPanel не хранит независимые значения свойств

exporter не берет данные из live widget tree

importer не пишет напрямую в canvas

serializer не зависит от UI



---

Удали или перепиши все места, где:

QWidget считается источником истины

свойства объекта читаются из canvas вместо документа

special-container логика дублируется в нескольких местах



---

3. Убери все обходные пути мутаций документа

Проверь, что любое изменение формы идет только так:

UI → DocumentController → FormDocument


Исправь все места, где есть:

PropertyPanel -> document напрямую

CanvasEditor -> document напрямую

FormItemView -> document напрямую



---

4. Зафиксируй единый refresh pipeline

После любого завершенного действия должен срабатывать один и тот же принцип.


---

Для простого property change

1. DocumentController меняет документ


2. flush_json_snapshot()


3. canvas.refresh_view(entity_id)


4. property_panel.rebuild()




---

Для структурного изменения

1. DocumentController меняет документ


2. flush_json_snapshot()


3. canvas.rebuild_all()


4. property_panel.rebuild()




---

Структурными изменениями считай:

add/remove page

delete subtree

create special-container

load document

import from python

reparent between container contexts



---

5. Стабилизируй selection logic

Приведи выбор к одному окончательному правилу.


---

Источник истины выбора

Только DocumentController.state.selected_entity_id


---

Canvas

Только показывает выделение


---

PropertyPanel

Только перестраивается по текущему selected state


---

Запрети

хранить отдельный selected state внутри PropertyPanel

хранить отдельный selected state внутри FormItemView как источник истины

держать независимый selected object внутри CanvasEditor



---

6. Приведи сценарий выбора к единому потоку

Сделай так:

Клик по объекту

1. FormItemView сообщает canvas


2. canvas сообщает контроллеру


3. контроллер обновляет selected id


4. контроллер обновляет canvas


5. контроллер обновляет PropertyPanel




---

Клик по пустому месту

1. canvas сообщает контроллеру None


2. контроллер очищает selection


3. canvas снимает выделение


4. PropertyPanel показывает форму




---

7. Стабилизируй delete-сценарии

Проверь отдельно все удаления.


---

Leaf-object

После удаления:

объект исчез с canvas

выбранность сброшена

PropertyPanel показывает форму

JSON обновлен



---

Обычный контейнер

После удаления:

исчезает весь subtree

canvas не содержит битых ссылок на дочерние view

PropertyPanel сброшена

JSON обновлен



---

Special-container

После удаления:

исчезает весь subtree

все internal-типы удалены

canvas полностью согласован

JSON обновлен



---

8. Убери нестабильные точечные удаления view

Если сейчас для сложных контейнеров удаление делается вручную по кускам и дает сбои, зафиксируй правило:

После удаления subtree special-container:

всегда canvas.rebuild_all()


Это лучше, чем полуточечная логика с ошибками.


---

9. Стабилизируй create-сценарии

Проверь отдельно:

создание пустой формы

загрузка JSON

загрузка Python

создание leaf-объекта

создание обычного контейнера

создание каждого special-container


После каждого create-сценария должно быть одновременно верно:

документ валиден

canvas валиден

PropertyPanel валидна

JSON snapshot валиден



---

10. Проведи ревизию special-container паттернов

Проверь, что все специальные контейнеры подчиняются одному общему принципу.


---

Page-based контейнеры

QTabWidget

QStackedWidget

QToolBox

QWizard


Общие правила:

сам контейнер видим пользователю

внутренние страницы существуют в документе

страницы не появляются в палитре

страницы не выбираются как обычные объекты формы

объекты падают в активную страницу

управление страницами идет через PropertyPanel



---

Content-based контейнеры

QScrollArea


Общие правила:

сам контейнер видим

ContainerContent существует в документе

ContainerContent скрыт от пользователя

объекты падают в ContainerContent



---

Pane-based контейнеры

QSplitter


Общие правила:

сам контейнер видим

панели существуют в документе как SplitterPane

панели скрыты от пользователя как самостоятельные объекты

объекты падают в конкретную панель



---

11. Проверь, что эти паттерны не разъехались

Исправь все места, где:

одна page-модель ведет себя не так, как остальные

один internal-type показывается как объект, а другой нет

один special-container меняется через PropertyPanel, а другой напрямую


Выравнивай поведение по семействам.


---

Проверь и доведи:

17. Убери лишние каскадные обновления
