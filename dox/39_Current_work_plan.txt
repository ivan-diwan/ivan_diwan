The project is moving in the right direction.

This is supported by concrete signals:

- The recent work reduced large concentrations of responsibility instead of adding more.
- Architectural extractions were made at natural boundaries:
  - I/O moved out of `DocumentController`
  - property normalization moved out of `FormDocument`

In short:
the work is not drifting into cosmetic cleanup.
It is steadily reducing structural risk.


4. Main risks that still define the next stage

These are the main remaining pressure points of the codebase.

- `form_constructor/factory/widget_factory.py`
  Why it matters:
  - It is the next large per-widget behavior hub.
  - Runtime widget creation and property application are concentrated here.
  Main risk:
  - A change here can break preview/runtime behavior for many widgets at once.

- `form_constructor/ui/properties/property_panel.py`
  Why it matters:
  - It carries a lot of UI responsibilities in one place.
  - It likely mixes schema-driven editing, context-dependent UI sections, and special-case handling.
  Main risk:
  - It can become the main maintenance bottleneck on the editor side.

- Cross-layer rule duplication
  Affected files:
  - `form_constructor/document/property_normalizer.py`
  - `form_constructor/document/validator.py`
  - `form_constructor/factory/widget_factory.py`
  - `form_constructor/conversion/importer.py`
  - `form_constructor/conversion/exporter.py`
  Why it matters:
  - Some overlap is normal, but accidental duplication increases the chance of divergence.
  Main risk:
  - A rule change can be applied in one layer and silently missed in another.

- `dox/` as documentation source
  Why it matters:
  - The folder preserves history well, but is not yet a compact, up-to-date technical map.
  Main risk:
  - Knowledge remains spread between history notes, tests, and implementation details.


5. Current priorities in order

Priority 1: Decompose `WidgetFactory`

Target file:
- `form_constructor/factory/widget_factory.py`

Why this is first:
- After the completed controller/document refactors, this is the next biggest logic concentration.
- It likely contains the largest remaining switchboard of widget-specific runtime application logic.
- Refactoring it now continues the same architectural direction already proven to work well.

Desired result:
- The file becomes easier to navigate.
- Per-widget application logic is grouped more clearly.
- Shared property-application patterns become more explicit.
- Behavior stays unchanged.


Priority 2: Simplify `PropertyPanel`

Target files:
- `form_constructor/ui/properties/property_panel.py`
- `form_constructor/ui/properties/property_editor_factory.py`

Why this is second:
- Once `WidgetFactory` is safer, the next major maintainability gain is on the editor UI side.
- The property panel is likely the next area where complexity growth will hurt speed of change.

Desired result:
- UI logic is easier to reason about.
- Mode-specific behavior is less entangled.
- Special sections and schema-driven editors are easier to extend.


Priority 3: Clarify rule ownership between layers

Primary files:
- `form_constructor/document/property_normalizer.py`
- `form_constructor/document/validator.py`
- `form_constructor/factory/widget_factory.py`
- `form_constructor/conversion/importer.py`
- `form_constructor/conversion/exporter.py`

Desired layer split:
- Validator: rejects invalid state
- Normalizer: coerces raw values into acceptable state
- WidgetFactory: applies valid state to runtime widgets
- Importer/Exporter: translate formats and carry diagnostics

Why this is third and not first:
- It should be done after the large concentration points are easier to see.
- Otherwise there is a risk of trying to clarify ownership while the hosting files are still too dense.


6. Recommended execution sequence

The safest order for the current stage is:

1. Refactor `WidgetFactory` in small verified passes.
2. Keep behavior frozen while restructuring internal organization.
3. Add or tighten focused tests where `WidgetFactory` refactors need extra safety.
4. Move to `PropertyPanel` only after `WidgetFactory` stabilizes.
5. Revisit cross-layer rule ownership once both large hotspots are easier to inspect.
6. Update documentation when the new boundaries settle enough to describe clearly.
