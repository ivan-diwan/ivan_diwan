Промежуточный этап ревизии

Расположи этот этап строго между:

Девятая рабочая контрольная точка — устойчивый QWizard

и

Десятая рабочая контрольная точка — полная доводка PropertyPanel


Этот этап обязателен.

Не перепрыгивай через него.

Не переходи к полной доводке PropertyPanel, пока не выровнены базовые архитектурные контракты.


Причина введения этапа

К этому моменту система уже умеет:

обычные leaf-объекты

обычные контейнеры

QTabWidget

QScrollArea

QSplitter

QWizard


Но при сопоставлении текущего состояния кода с roadmap и рабочими checkpoint выявлены расхождения:

часть фундаментальных контрактов была запланирована раньше, чем special-container-этапы, но фактически осталась недоведенной

часть логики уже начала расползаться по слоям

часть требований checkpoint формально выполняется в UI, но не закреплена системно на уровне модели, валидатора, сериализации и центрального контроллера


Если не провести ревизию сейчас, дальше начнут накапливаться:

локальные исключения в PropertyPanel

дублирование бизнес-правил в CanvasEditor

дрейф API DocumentController

нестабильный JSON-контур

скрытые нарушения parent-child контрактов


Этот этап нужен не для косметики, а для укрепления основы перед следующим большим слоем работ.


---

1. Что показал анализ checkpoint и документации

Зафиксируй явно следующее.


Что уже частично предусмотрено документацией:

1. Полная доводка PropertyPanel в следующем checkpoint уже запланирована как отдельный большой этап.

2. Для PropertyPanel уже зафиксировано правильное направление:

не захардкоживать хаотичную логику по типам

опираться на WidgetRegistry

проводить изменения только через DocumentController

3. Для PythonExporter в следующих checkpoint уже зафиксирован правильный инженерный принцип:

строить экспорт только из документа

не строить экспорт из canvas

не латать exporter локальными костылями


Что НЕ покрыто отдельной корректировкой в текущих checkpoint:

1. доведение WidgetRegistry до полного контрактного API

2. доведение DocumentValidator до полноценного слоя проверки документа

3. выравнивание FormSerializer и JSON-контракта с документацией

4. выравнивание публичного контракта DocumentController

5. вынос или хотя бы нормализация общей drop-parent логики из CanvasEditor

6. фиксация единого системного parent-child контракта вместо частичных локальных проверок


Вывод:

нужен отдельный промежуточный ревизионный этап

и только после него можно безопасно переходить к полной доводке PropertyPanel


---

2. Цель промежуточного этапа

В этом этапе не добавляй новую пользовательскую функциональность.

Не добавляй новые special-container.

Не переходи к PythonExporter.

Не переходи к PythonImporter.


Задача этапа:

привести фундаментальные слои редактора к состоянию, в котором они:

соответствуют документации

не противоречат друг другу

образуют устойчивый контракт между слоями

не требуют локальных подпорок при следующем расширении системы


Итог этапа должен быть таким:

WidgetRegistry становится полноценным контрактным источником метаданных типов

DocumentValidator становится реальным слоем проверки документа, а не формальностью

JSON-контур становится двусторонним и устойчивым

parent-child правила проверяются единообразно

DocumentController фиксируется как центральная точка команд и обновления snapshot

CanvasEditor перестает нести лишнюю бизнес-логику, которая должна жить глубже

PropertyPanel получает чистую опору для следующего этапа, а не продолжает расти поверх сырого фундамента


---

3. Что признать проблемой до начала работ

Перед началом реализации зафиксируй как реальные архитектурные проблемы:

1. WidgetRegistry пока реализован как минимальное хранилище определений, а не как полноценный контрактный слой.

2. DocumentValidator пока не выполняет тот набор проверок, который уже ожидался по roadmap.

3. FormSerializer и FormDocument пока не образуют гарантированно устойчивый двусторонний цикл сериализации и десериализации.

4. Parent-child правила проверяются частично и не через один централизованный контракт.

5. DocumentController уже стал фактическим центром действий, но его публичный API еще не выровнен как единый архитектурный контракт.

6. CanvasEditor уже содержит нарастающую специальную логику для контейнеров и рискует превратиться в комбайн if-веток.

7. PropertyPanel уже накопил ручную логику по типам, и без укрепления основы следующий этап быстро превратится в набор костылей.


---

4. Что НЕ делай в этом этапе

Не расширяй палитру новыми типами.

Не добавляй новые special-container.

Не занимайся косметическим UX.

Не делай полноценную перестройку PropertyPanel раньше времени.

Не переписывай всю систему целиком ради абстрактной чистоты.

Не размазывай изменения по всему проекту без четкой причины.


Этап должен быть ревизионным и стабилизирующим.

Он не должен превращаться в бесконечный рефакторинг ради рефакторинга.


---

5. Блок A — доведи WidgetRegistry до документированного контрактного слоя

В roadmap для WidgetRegistry уже был зафиксирован более полный контракт.

Теперь доведи registry до этого состояния.


В registry/widget_registry.py обеспечь устойчивый внешний API уровня:

register_type(definition)

get_type(type_name)

has_type(type_name)

list_palette_types()

list_palette_groups()

get_default_size(type_name)

get_default_properties(type_name)

get_name_prefix(type_name)

get_property_schema(type_name)

can_parent(parent_type, child_type)

get_allowed_children(type_name)

get_special_actions(type_name)

get_auto_create_children(type_name)


Допускается сохранить старые короткие alias-методы:

register(...)

get(...)

all(...)

но внешний контракт должен быть уже приведен к документированному виду.


Смысл:

любой слой выше registry не должен угадывать структуру definition вручную,
если нужную информацию можно получить из методов registry.


---

6. Блок B — зафиксируй единый parent-child контракт

Система не должна проверять допустимость связки родитель-потомок разрозненно по нескольким местам.


Сделай единый путь проверки:

parent_type

child_type

registry.can_parent(parent_type, child_type)


Проверь обе стороны контракта:

allowed_parent_types у child

allowed_child_types у parent


Если позже понадобится direct_children_only,
заложи под это место сейчас,
даже если полная логика будет включена позже.


После этого:

FormDocument.create_entity(...)

операции reparent

валидация документа

drop-разрешения

должны опираться на один и тот же контракт,
а не на локальные частные проверки.


---

7. Блок C — доведи DocumentValidator

В document/validator.py реализуй полноценный слой проверки документа.


Поддержи минимум такие точки входа:

validate_document(document)

validate_entity(entity, registry)

validate_parent_child(parent_type, child_type, registry)


Проверь:

уникальность id

существование parent_id

валидность type

валидность geometry

допустимость parent-child

обязательные поля

корректность form root

корректность internal-типов

порядок children по order там, где он важен


Для geometry зафиксируй минимальный контракт:

x

y

width

height


Не ограничивайся проверкой только width > 0 и height > 0 у формы.


Validator должен выявлять не только явную поломку,
но и скрытые структурные нарушения документа,
которые потом ломают canvas, exporter или importer.


---

8. Блок D — приведи JSON-контур к рабочему контракту

В serialization/ и связанных слоях добейся полного соответствия документации.


JSON-контур должен иметь устойчивую форму:

meta

format_version

document_type

form

objects


Зафиксируй:

document_type = "pyside6_form"


Убедись, что:

serialize_to_dict(document)

serialize_to_json(document)

deserialize_from_dict(data)

deserialize_from_json(payload)

образуют корректный двусторонний цикл.


Особенно проверь:

FormDocument при десериализации создается с корректным widget_registry

internal-сущности не теряются

order не теряется

properties не теряются

geometry сохраняется без побочных искажений


После этого полный цикл должен работать так:

создать документ

сериализовать в dict

сериализовать в JSON

загрузить обратно

получить эквивалентный документ


---

9. Блок E — выровняй границы ответственности FormDocument

FormDocument должен быть моделью документа,
а не местом, куда постепенно стекается разнородное знание обо всем приложении.


Проверь и приведи к такому принципу:

FormDocument хранит данные и операции модели

не знает о QWidget-дереве

не знает о canvas

не знает о PropertyPanel

не знает о runtime-дереве живых виджетов формы


Разрешено:

логика дерева сущностей

логика специальных операций документа

логика внутренних сущностей и их структурных зависимостей


Не разрешено:

UI-зависимые решения

визуальные правила отображения

знание о selection-механике canvas


Если найдешь смещение границ,
устраняй его сейчас,
пока слой еще не разросся сильнее.


---

10. Блок F — приведи DocumentController к стабильному центральному контракту

DocumentController уже фактически стал центром пользовательских действий.

Теперь зафиксируй это архитектурно.


Добейся, чтобы контроллер был единственной явной точкой, через которую проходят:

создание документа

выбор объекта

очистка выбора

изменение свойств

изменение геометрии

удаление

сериализация snapshot

сохранение документа

будущая загрузка документа


Выровняй публичный API контроллера хотя бы до уровня:

new_document() или create_new_document()

select_entity(...)

clear_selection()

delete_entity(...)

delete_selected_entity()

update_entity_property(...)

update_entity_geometry(...)

flush_json_snapshot()


Если старые имена уже используются,
сохрани совместимость,
но введи явный центральный контракт.


Особенно важно:

flush_json_snapshot() должен существовать явно,
а не только как скрытый побочный вызов из внутренних методов.


---

11. Блок G — сократи архитектурную нагрузку CanvasEditor

CanvasEditor не должен превращаться в бесконечный список hardcoded special-container правил.


На этом этапе не обязательно делать большой рефакторинг.

Но обязательно проведи ревизию и зафиксируй правила:

CanvasEditor отвечает за:

визуальную сборку дерева view

маршрутизацию drop

selection

визуальные операции move и resize


Но не должен:

дублировать бизнес-правила документа

самостоятельно определять parent-child допустимость в обход registry и document

разрастаться неконтролируемыми if-ветками под каждый новый special-container


Если для этого нужен отдельный слой вида:

drop_target_resolver.py

его разрешено создать,
но только если это реально уменьшает сложность,
а не создает пустую промежуточную обертку.


---

12. Блок H — подготовь основу для следующего этапа полной доводки PropertyPanel

В этом этапе не завершай всю полную перестройку панели.

Но убери то, что точно мешает ей стать нормальным модулем в следующем checkpoint.


Сделай:

PropertyPanel там, где это возможно, уже должен смотреть на schema из registry

internal-типы не должны случайно получать неподходящие geometry-редакторы

зависимость панели от конкретных типов должна быть уменьшена везде,
где это можно сделать без ломки текущего рабочего поведения


Но оставь следующему отдельному этапу:

полный переход на schema-driven panel

спец-редакторы enum, list, multiline

полную унификацию rebuild-flow

полное выравнивание special-блоков панели


Этот ревизионный этап должен подготовить для следующего checkpoint прочную опору,
а не пытаться завершить две большие задачи сразу.


---

13. Обязательные сценарии ревизии

Этап нельзя считать завершенным,
если не подтверждены следующие сценарии.


Сценарий 1

Создать новый документ.

Получить валидный FormDocument.

Прогнать документ через DocumentValidator.

Не получить ошибок.


Сценарий 2

Создать документ.

Добавить:

обычный контейнер

QTabWidget

QScrollArea

QSplitter

QWizard

Добавить во внутренние области дочерние объекты.

Прогнать весь документ через валидатор.

Получить валидный результат.


Сценарий 3

Сериализовать документ в dict.

Сериализовать в JSON.

Загрузить обратно.

Прогнать загруженный документ через валидатор.

Сравнить ключевые поля с исходным документом.


Сценарий 4

Проверить недопустимые parent-child связки.

Например:

special-container туда, где он еще запрещен

internal-тип как пользовательский drop

некорректный child у родителя


Система должна:

не принимать такую структуру

не загрязнять документ

не оставлять полусобранное состояние


Сценарий 5

Изменение свойств и геометрии любого уже поддержанного объекта

должно проходить только через DocumentController

и после завершения давать корректный JSON snapshot


Сценарий 6

Все уже закрытые рабочие этапы должны сохраниться в рабочем состоянии:

QTabWidget

QScrollArea

QSplitter

QWizard


Ревизия не должна ломать уже подтвержденные пользовательские сценарии.


---

14. Что считать результатом этого этапа

Этап считается закрытым только если:

1. WidgetRegistry стал полноценным контрактным слоем.

2. Validator проверяет реальную структуру документа, а не только формальные размеры формы.

3. JSON-контур устойчив и двусторонен.

4. Controller имеет явный центральный контракт.

5. Parent-child правила проверяются единообразно.

6. CanvasEditor не дублирует бизнес-правила хаотично.

7. База подготовлена к следующему этапу полной доводки PropertyPanel.


---

15. Следующий шаг после этого этапа

Только после устойчивого прохождения промежуточной ревизии переходи к:

Десятая рабочая контрольная точка — полная доводка PropertyPanel


Порядок после этого этапа должен быть таким:

QWizard закрыт

промежуточная архитектурная ревизия закрыта

только потом полная доводка PropertyPanel


---

16. Главный принцип этапа

Этот этап нужен не для косметики.

Он нужен, чтобы:

не подпирать систему локальными исключениями

не размывать контракт между слоями

не переносить фундаментальные проблемы дальше в PropertyPanel, exporter и importer


Если по итогам ревизии останется выбор:

быстрее оставить как есть

или

чуть дольше, но привести основу к устойчивой архитектуре


выбирай второе.

17. Фактический статус прохождения этапа

По состоянию на текущий момент промежуточный этап ревизии считается пройденным на уровне базовых контрактов и обязательных сценариев.


Что фактически доведено:

1. WidgetRegistry расширен до контрактного API и используется как источник метаданных не только для палитры, но и для validator, controller, canvas и PropertyPanel.

2. Parent-child правила проверяются единообразно через registry.can_parent(...), а не разрозненными локальными проверками.

3. DocumentValidator проверяет:

структуру form root

корректность entity id

parent-child связи

order детей

geometry

property schema

allowed_values

инварианты уже поддержанных special-container

4. JSON-контур выровнен:

document_type = "pyside6_form"

serializer и deserializer работают в обе стороны

load/save из файла подключены

round-trip проходит через validator

5. DocumentController закреплен как центральная точка команд и snapshot-flow.

6. CanvasEditor и DropTargetResolver больше не растут как бесконтрольные списки hardcoded if-веток по special-container.

7. PropertyPanel переведен на частично schema-driven основу и подготовлен к следующему checkpoint полной доводки.

8. Save/Load JSON подключены в MainEditorWindow и работают через controller.


Какие обязательные сценарии подтверждены:

1. Создание нового документа и его валидация.

2. Создание документа с:

обычным контейнером

QTabWidget

QScrollArea

QSplitter

QWizard

и дочерними объектами внутри их допустимых внутренних областей.

3. Полный dict/json/file round-trip с последующей повторной валидацией документа.

4. Отклонение недопустимых parent-child связей и user-drop для internal типов.

5. Изменение свойств и геометрии только через DocumentController с корректным snapshot.

6. Сохранение работоспособности уже закрытых этапов:

QTabWidget

QScrollArea

QSplitter

QWizard


Вывод:

после этого этапа допустим переход к следующему checkpoint:

Десятая рабочая контрольная точка — полная доводка PropertyPanel.
